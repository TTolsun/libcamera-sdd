## T1: 공통 계층과 장치 구현

실제 답: 공통 libcamera 프레임워크는 Camera를 통해 카메라 구성·제어·캡처의 API를 제공하고, 준비·대기 큐 등 공통 처리를 담당한다. 커널 드라이버는 하드웨어를 직접 제어하며 V4L2 계열의 저수준 API를 노출한다. 장치별 PipelineHandler는 필요한 미디어 장치를 매칭·확보해 Camera를 만들고 등록해야 한다. 장치별 완료 통지도 남는다. completeBuffer로 마지막 버퍼가 끝나더라도 요청이 자동 완료되지는 않으므로 completeRequest를 명시 호출해야 한다. 애플리케이션과 상위 프레임워크는 libcamera 프로젝트 범위 밖이다. 문서가 나열한 전용/범용 플랫폼과 빌드 선택을 확인해야 하며 공통 API의 존재를 모든 하드웨어 지원 보장으로 해석할 수 없다. 상태에 영향을 주는 Camera 함수의 동기화도 필요할 때 호출자가 책임진다.

근거와 조회 경로:

자동 편집 의견: 책임의 근거는 찾을 수 있다. 공통 계층을 설명하는 절이 곧바로 내부 큐 이름으로 전환되므로 도입 범위를 판단하는 타팀 독자는 장치 구현의 필수 의무와 큐 구현 상세를 구분해서 읽어야 한다. 네 계층·하드웨어 경계·완료 경계에는 각각 그림 원문과 대응 질문이 존재한다. 화면에서 이 그림들이 얼마나 읽기 쉬운지는 평가하지 않았다. API 추상화가 구체적으로 줄여 주는 작업은 발췌가 도입 문장에서 끝난다는 한계도 본문에 명시되어 있다.

## T2: 내장 벤치마크

실제 답: DebayerCpu 내장 벤치마크는 통계 수집과 디베이어링의 처리 시간만 포함한다. 프레임 캡처와 프레임 출력 시간은 제외한다. Software ISP를 사용하는 파이프라인에서 cam 또는 qcam을 실행해 사용할 수 있다. 따라서 이 벤치마크를 전체 캡처·출력 지연이나 제품 성능의 근거로 확대하지 않는다.

자동 편집 의견: 포함·제외를 같은 짧은 문단에서 찾을 수 있다. 이 범위 설명은 짧아 그림을 추가하지 않아도 질문에 답한다. DebayerCpu와 디베이어링의 용어는 타팀 독자가 별도 확인할 수 있지만 이번 답 찾기를 막지는 않았다. 실행값, 실행 환경의 성능, 실제 제품 적용 결과는 이 시험에서 확인하지 않았다.

## S: 추가 조회 없이 적은 설명

20:11:52 UTC에 request-lifecycle.html과 request-diagnosis.html의 본문을 읽은 후, 추가 문서 조회 없이 다음 설명을 적었다. 이전 시험과 방금 읽은 내용이 문맥에 남아 있으므로 사람의 독립 회상 성과가 아니다.

성공 반환은 요청을 다음 비동기 처리 단계로 넘기도록 접수했다는 뜻이다. 그 순간 장치가 프레임 처리를 끝냈다는 뜻은 아니다. 준비와 큐 제한, 장치 제출, 버퍼 완료를 거친 다음 요청 완료를 별도로 알려야 한다. 마지막 버퍼가 끝나도 요청 완료가 자동으로 전달되지 않는다. 따라서 성공 반환 뒤 알림이 없다는 사실만으로 원인을 장치나 콜백에 확정해서는 안 된다.

첫 조회 경로는 candidate/index.html → request-lifecycle.html#제출에서-완료까지 → request-diagnosis.html#실패-위치별-확인-순서이다. 자기 말 설명을 저장한 뒤 index.html로 돌아가 request-lifecycle.html을 다시 찾았다. [Camera::queueRequest 페이지 내 발췌](../candidate/request-lifecycle.html#source-28d007de6ad1a8a5)에서 ConnectionTypeQueued 호출 후 `return 0;`과 별도의 requestCompleted 계약을 확인했다. [비동기 전달 발췌](../candidate/request-lifecycle.html#source-0470759dc8387e9a)에서는 메시지 게시와 Blocking 대기 경로의 구분을 확인했다. 재조회 완료 시각은 20:13:18 UTC이다. S 단독 소요 시간은 미측정이며 R 메모·중단·재탐색 시간이 섞여 있다.

자동 편집 의견: 접수 성공과 완료의 차이는 [제출에서 완료까지](../candidate/request-lifecycle.html#제출에서-완료까지)의 첫 문장에서 답한다. 함수 이름이 비슷한 queueRequest/queueRequestDevice와 버퍼·요청 두 종류의 완료를 구분해야 한다. 각 단계의 그림 원문과 질문은 존재하지만 화면에서 연속된 그림의 실제 탐색 부담은 미확인이다. 실행에서 알림이 없는 원인은 이 문서 읽기만으로 알아낼 수 없으며 아직 미확인이다.

## R: 조회를 중단하기 전에 남긴 자유 메모

현재 알고 있는 실행 관측은 과업이 준 제출 함수 성공 반환과 완료 알림 부재뿐이다. 실제 애플리케이션이나 장치는 실행하지 않았다. 문서에서 조사 순서를 확인했으며, 아직 어느 단계에서 멈췄는지는 모른다.

다시 시작할 주소는 candidate/index.html이다. 요청 처리와 문제 진단에서 접수/완료 차이를 찾고, 구성과 요청 오류 조사에서 실패 위치별 확인 순서로 간다. 제출 반환값과 요청 식별을 먼저 남긴다. 다음 관측은 대기 요청 존재, queuedRequests_ 크기와 maxQueuedRequestsDevice_ 비교, 선두 prepared_이다. 그 뒤 cancelled_와 queueRequestDevice ret를 확인한다. 버퍼마다 completeBuffer 알림과 반환을 보고, 마지막에도 completeRequest 명시 호출이 필요한지 확인한다. 뒤 요청만 완료됐으면 큐 앞의 RequestPending 때문에 반환이 멈췄는지 확인한다.

미확인점은 실제 요청 ID, 버퍼 수·완료 수, 준비 상태, 큐 크기, 장치 제출 결과, 취소 상태, completeRequest 호출과 앞선 요청 상태, 대상 앱의 신호 연결/수신 스레드다. 각 단계의 관측을 실제로 얻기 전에는 다음 원인을 확정하지 않는다. 공개 가상 프로브 결과를 이 실행의 결과로 옮기지 않는다.

근거 메모는 request-lifecycle.html#제출에서-완료까지, request-diagnosis.html#실패-위치별-확인-순서이다. 두 버퍼 중 하나만 완료됐다는 질문은 같은 진단 문서의 버퍼 완료와 명시적 요청 완료의 경계에서 이어간다.

## R: 자동 탐색 재개

메모 저장 시각은 20:12:45 UTC이다. 문서 조회를 중단한 뒤 20:12:55 UTC에 자기 메모만 다시 읽었고 20:13:08 UTC에 candidate/index.html로 돌아갔다. 중단 구간은 약 23초였다. **이 절차는 자동 탐색 재개이며 사람의 5분 주의 중단이 아니다.** 이전/현재 문서 내용이 에이전트 문맥에 남아 있으므로 자기 메모만 재조회한 절차가 사람의 망각이나 회복 능력을 입증하지 않는다.

재개한 상태 설명: 요청 접수는 성공했지만 완료 경로에서 처음 빠진 관측 위치를 모른다. 다음 행동은 진단 문서에서 큐 한도와 선두 준비 상태를 확인할 위치를 다시 찾는 것이다. 실제로 index.html의 요청 처리와 문제 진단, 구성과 요청 오류 조사 링크를 찾은 뒤 [실패 위치별 확인 순서](../candidate/request-diagnosis.html#실패-위치별-확인-순서)를 재조회했다. 큐 비교 → prepared_ → cancelled_/장치 제출 ret → 버퍼별 알림과 completeBuffer 반환 → completeRequest 명시 호출 → 큐 선두 RequestPending 분기를 다시 찾았다. [페이지 내부 발췌](../candidate/request-diagnosis.html#source-01ad7c6605c3296a)에서 버퍼와 요청 완료 경계를 확인했다.

경로: 자기 메모 → candidate/index.html → request-diagnosis.html#실패-위치별-확인-순서 → #버퍼-완료와-명시적-요청-완료의-경계 → #source-01ad7c6605c3296a → #제출-큐의-선두-상태와-반환-순서. 되돌아간 시작 주소는 index.html이다. 20:12:55~20:13:18 UTC의 도구 경과는 약 23초였지만 S/T2/X의 근거 확인도 포함하므로 R 단독 시간은 미측정이다.

확인한 것은 조사 위치다. 과업에서 준 실행 관측 외에 실제 값을 얻지는 않았다. 미확인점은 위 메모와 같으며, 최초로 관측되지 않는 단계를 찾기 전에는 원인을 정할 수 없다. 자동 편집 의견으로는 `현재 상태 / 실제 관측 / 미확인 / 다음 분기 / 앵커`를 함께 남긴 메모가 재탐색에 쓸 수 있었다. 이것을 사람의 기억 부담 개선 점수로 환산하지 않는다. 긴 진단 문장에 여러 관측식이 있으므로 자신의 실행값을 별도 메모로 분리할 필요가 있다. 그림 렌더링과 상세 링크의 클릭 동작은 미확인이다.

## X: 두 버퍼 중 하나만 완료

실제 답: 두 버퍼 중 한 버퍼만 완료되고 나머지는 아직 미완료라는 상태가 확인됐다면 요청의 모든 버퍼가 완료됐다고 단정할 수 없다. completeBuffer는 모든 버퍼가 끝나야 true를 반환하므로 이 상태의 완료 집계는 false에 해당한다. 한 버퍼의 완료는 요청 전체의 완료가 아니다. 두 버퍼가 모두 끝나더라도 요청은 자동 완료되지 않아 completeRequest를 명시 호출해야 한다.

`완료 알림을 하나만 관찰했다`는 말이라면 두 번째 버퍼의 실제 미완료까지 단정하지 않는다. 같은 요청의 두 버퍼인지, 두 번째의 추적 상태와 알림 관측 누락 여부를 확인한다. 두 번째가 실제 미완료이면 그 처리/취소 경로를 조사한다. 모두 완료되었다면 completeRequest 명시 호출 여부를 확인한다. 그 호출이 있었어도 반환이 없다면 제출 큐 선두가 RequestPending으로 남아 뒤의 완료 요청 반환을 막는지 조사한다. 이 조건만으로 장치 고장이나 신호 연결 오류를 확정할 수 없다.

근거: [버퍼 완료와 명시적 요청 완료의 경계](../candidate/request-diagnosis.html#버퍼-완료와-명시적-요청-완료의-경계), [같은 페이지의 completeBuffer/completeRequest 발췌](../candidate/request-diagnosis.html#source-01ad7c6605c3296a), [제출 큐 선두와 반환 순서](../candidate/request-diagnosis.html#제출-큐의-선두-상태와-반환-순서).

경로는 R에서 재개한 진단 문서 → 버퍼 완료 본문 → 내부 발췌 → 선두 상태 본문이다. 외부 소스는 열지 않았다. X 단독 시간은 미측정이며 20:13:18 UTC의 재조회에 포함된다. 실제 두 버퍼의 상태와 이벤트 관측은 이 시험에서 수행하지 않았으므로 미확인이다.
