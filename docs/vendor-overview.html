이 문서의 용어: Pipeline Handler, HAL, IPU3, RK3399 외 1개
  • Pipeline Handler: 특정 하드웨어 플랫폼(IPU3, RKISP1 등)의 미디어 장치를 찾아 카메라를 만들고, 요청을 장치에 넣고 완료를 돌려주는 libcamera 구성 요소입니다. 플랫폼마다 하나씩 있습니다.
  • HAL (Hardware Abstraction Layer): 운영체제가 제조사마다 다른 하드웨어를 같은 인터페이스로 다루게 하는 계층입니다. 이 프로젝트의 최종 적용 대상은 사내 Android Camera HAL입니다.
  • IPU3 (Intel Image Processing Unit 3): 일부 Intel 노트북 프로세서에 들어 있는 카메라 ISP입니다. libcamera에는 이 장치용 Pipeline Handler와 IPA가 있습니다.
  • RK3399: Rockchip이 만든 시스템 반도체(SoC)의 이름입니다. 이 문서에서는 rkisp1 파이프라인 핸들러로 지원한다고 문서가 적은 플랫폼으로 나옵니다.
  • IPU6: Intel 이미지 처리 장치(IPU) 계열의 한 세대 이름입니다. 이 문서에서는 전용 파이프라인 핸들러 없이 범용(simple) 파이프라인으로 지원한다고 문서가 적은 플랫폼으로 나옵니다.

다른 용어는 용어집에서 찾을 수 있습니다.

무엇이며 누구의 어떤 문제를 푸는가

libcamera는 Linux, Android, ChromeOS를 위한 오픈 소스 복합 카메라 지원 라이브러리입니다. Linux 커널 장치 드라이버와 연결하고 개발자에게 직관적인 API를 제공해 Linux 시스템에서 복합 카메라로 이미지를 캡처하는 복잡한 작업을 단순화합니다. 드라이버를 사용해 동작하는 카메라 스택을 제공하는 일은 사용자 공간의 책임이며, 벤더들이 보통 애플리케이션 개발자를 위한 공통 아키텍처나 API 없이 각자 구현해 왔습니다. 하드웨어 파이프라인과 커널 API에서 이를 표현하는 방식이 서로 달라 맞춤 처리가 필요한 경우가 많아 이 작업은 복잡합니다.

libcamera는 Linux 기반 시스템을 위한 완전한 카메라 스택을 제공합니다. 커널의 API를 통해 카메라에서 원하는 결과를 얻는 데 필요한 하드웨어 구성과 이미지 제어 알고리즘을 추상화하여, 개발자가 이 작업을 간단하고 일관된 방법으로 다루게 합니다. 카메라 스택의 맨 아래 계층인 커널 드라이버는 카메라 하드웨어를 제어하고 Linux 커널의 V4L2 API 계열을 통해 사용자 공간에 저수준 인터페이스를 제공합니다. 이 API에는 Media Controller API, V4L2 Video Device API, V4L2 Subdev API가 있습니다.

그 위의 libcamera 프레임워크는 스택의 핵심 계층입니다. 핵심 구성 요소인 libcamera가 카메라 장치의 모든 제어를 처리하고 상위 계층에 네이티브 C++ API를 제공합니다. 선택적인 언어 바인딩을 사용하면 다른 프로그래밍 언어에서도 libcamera와 인터페이스할 수 있습니다.

그 위의 libcamera adaptation은 다른 프레임워크에서 libcamera와 인터페이스하는 구성 요소를 통칭합니다. 예로는 V4L2 호환 계층, gstreamer libcamera 요소, libcamera 기반 Android 카메라 HAL 구현이 있습니다. 맨 위의 애플리케이션과 상위 프레임워크는 libcamera 프레임워크 또는 libcamera adaptation을 기반으로 합니다. 이 계층은 libcamera 프로젝트의 범위 밖에 있습니다.

지원하는 하드웨어와 빌드 선택

문서는 전용 파이프라인 핸들러로 지원하는 하드웨어 플랫폼으로 Arm Mali-C55, Intel IPU3 (ipu3), NXP i.MX8MP (imx8-isi 및 rkisp1), RaspberryPi 3, 4 및 zero (rpi/vc4), Rockchip RK3399 (rkisp1)를 나열합니다. 문서에 명시된 범용 지원 대상은 USB 비디오 장치 클래스 카메라(uvcvideo), iMX7·IPU6·Allwinner Sun6i(simple), 테스트 용도의 가상 미디어 컨트롤러 드라이버(vimc)입니다.

빌드할 파이프라인 핸들러는 배열 옵션 pipelines에서 선택합니다. 기본값은 auto이며, 대상 아키텍처에 적용되는 모든 파이프라인을 빌드합니다. all을 선택하면 모든 파이프라인을 빌드하며, auto와 all을 함께 선택하면 all이 우선합니다. 개별 선택 값은 imx8-isi, ipu3, mali-c55, rkisp1, rpi/pisp, rpi/vc4, simple, uvcvideo, vimc, virtual입니다.

장치 구현자가 공통 계층에서 얻는 것

공통 PipelineHandler::queueRequest는 캡처 요청을 처리하도록 먼저 내부 대기 요청 목록에 추가합니다. 이 요청은 파이프라인 핸들러에 큐잉할 준비가 되었는지 확인하는 준비 과정을 거칩니다. 이 함수는 대기 요청 큐를 순회하며 준비된 요청을 최대 maxQueuedRequestsDevice_개까지 이 함수에 큐잉된 순서대로 파이프라인 핸들러에 전달합니다. 요청이 준비 단계에서 실패하거나 파이프라인 핸들러가 요청을 하드웨어 큐에 등록하는 데 실패하면 해당 요청을 취소합니다.

대기열에 넣은 요청을 추적하면 파이프라인 핸들러를 stop()으로 정지할 때 모든 요청이 자동으로 완료되며, 파이프라인 핸들러는 completeRequest()로 요청 완료를 알려야 합니다. 반면 completeBuffer()에서 마지막 버퍼가 완료되어도 요청은 자동으로 완료되지 않으므로 파이프라인 핸들러가 completeRequest()를 명시적으로 호출해야 합니다.

장치 요청 한도와 대기 큐

PipelineHandler 생성자 선언에서 maxQueuedRequestsDevice의 기본값은 32입니다. maxQueuedRequestsDevice_는 파이프라인 핸들러가 한 시점에 기반 하드웨어에 대기시켜야 하는 요청 수를 제한하며, 나머지 요청은 내부 대기 큐에서 기다립니다. 애플리케이션이 장치 한도보다 많은 요청을 제출하면 나머지 요청은 나중에 하드웨어에 대기열로 등록될 때까지 내부 대기 큐에서 기다립니다.

The camera stack comprises four software layers. From bottom to top:

* The kernel drivers control the camera hardware and expose a
  low-level interface to userspace through the Linux kernel V4L2
  family of APIs (Media Controller API, V4L2 Video Device API and
  V4L2 Subdev API).

* The libcamera framework is the core part of the stack. It
  handles all control of the camera devices in its core component,
  libcamera, and exposes a native C++ API to upper layers. Optional
  language bindings allow interfacing to libcamera from other
  programming languages.

  Those components live in the same source code repository and
  all together constitute the libcamera framework.

* The libcamera adaptation is an umbrella term designating the
  components that interface to libcamera in other frameworks.
  Notable examples are a V4L2 compatibility layer, a gstreamer
  libcamera element, and an Android camera HAL implementation based
  on libcamera.

  Those components can live in the libcamera project source code
  in separate repositories, or move to their respective project's
  repository (for instance the gstreamer libcamera element).

* The applications and upper level frameworks are based on the
  libcamera framework or libcamera adaptation, and are outside of
  the scope of the libcamera project.
