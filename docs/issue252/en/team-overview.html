Terms in this document: V4L2, Pipeline Handler, HAL, IPA
  • V4L2 (Video4Linux2): The API through which the Linux kernel handles cameras and video devices. libcamera uses this API to control the sensor and ISP devices.
  • Pipeline Handler: A libcamera component that finds the media device of a specific hardware platform (IPU3, RKISP1, etc.), creates cameras, passes requests to the device, and returns their completion. There is one per platform.
  • HAL (Hardware Abstraction Layer): A layer that lets the operating system handle hardware that differs by manufacturer through the same interface. The final deployment target of this project is the in-house Android Camera HAL.
  • IPA (Image Processing Algorithms): A separate module (.so) that contains image quality algorithms. It reads the statistics sent by the ISP and calculates the ISP settings to use for the next frame. It is separated from the libcamera core so that manufacturers can provide it without publishing its source.

Other terms can be found in Glossary.

What it does

libcamera is an open-source complex camera support library for Linux, Android, and ChromeOS. It connects to Linux kernel device drivers and provides an intuitive API to developers, reducing the complexity of capturing images from complex cameras on Linux systems.

The responsibility for providing a working camera stack using these drivers lies in userspace. Vendors commonly implement this separately, and there is no common architecture or API for application developers. Because hardware pipelines and their representation in the kernel APIs differ, bespoke handling often is required.

libcamera provides a complete camera stack for Linux-based systems. It abstracts the hardware configuration and image control algorithm operations that are performed through kernel APIs to obtain desired results from the camera, reducing them to a simple and consistent method for developers. The camera stack consists of four layers, from bottom to top: kernel drivers, the libcamera framework, the libcamera adaptation, and applications and upper-level frameworks.

Inputs received

Kernel drivers control the camera hardware and, through the Media Controller API, V4L2 Video Device API, and V4L2 Subdev API, which belong to the V4L2 API family of the Linux kernel (the interface through which programs handle devices), provide a low-level interface to user space. It is not confirmed which specific inputs libcamera receives from the lower layers for camera control. The Camera Manager, which is the camera manager, enumerates the cameras that libcamera supports and creates a Pipeline Handler to manage each camera. Only one Camera Manager runs per application, and it ensures that only a single application at a time takes control of a camera device.

What It Provides

libcamera provides a native C++ API so that applications can control camera devices. Optional language bindings allow libcamera to be connected from other programming languages.

The libcamera adaptation is an umbrella term for the components that interface with libcamera in other frameworks. Examples include a V4L2 compatibility layer, the gstreamer libcamera element, and an Android camera hardware abstraction layer (HAL) implementation based on libcamera. These components may reside in separate source code repositories within the libcamera project, or may move to the repository of their respective projects.

Boundaries with other teams and layers

Applications (application programs used by users) and upper-level frameworks (upper-level software foundations that support applications) are based on the libcamera framework or a form that applies libcamera, and are outside the scope of the libcamera project.

Device vendors must contribute the Pipeline Handler, which is part of the libcamera codebase, upstream. The Pipeline Handler configures the device's camera processing path based on stream configuration, manages execution and scheduling when needed, creates Camera instances, and is responsible for interactions with the device. Device vendors may separately provide an IPA Module that runs algorithms such as automatic exposure, automatic white balance, and automatic focus on the CPU and controls hardware image processing according to parameters from upper layers. IPA Module included in libcamera is covered by a free software license, and external modules may be distributed under a closed-source license if they do not include source code from the libcamera project.

The camera stack comprises four software layers. From bottom to top:

* The kernel drivers control the camera hardware and expose a
  low-level interface to userspace through the Linux kernel V4L2
  family of APIs (Media Controller API, V4L2 Video Device API and
  V4L2 Subdev API).

* The libcamera framework is the core part of the stack. It
  handles all control of the camera devices in its core component,
  libcamera, and exposes a native C++ API to upper layers. Optional
  language bindings allow interfacing to libcamera from other
  programming languages.

  Those components live in the same source code repository and
  all together constitute the libcamera framework.

* The libcamera adaptation is an umbrella term designating the
  components that interface to libcamera in other frameworks.
  Notable examples are a V4L2 compatibility layer, a gstreamer
  libcamera element, and an Android camera HAL implementation based
  on libcamera.

  Those components can live in the libcamera project source code
  in separate repositories, or move to their respective project's
  repository (for instance the gstreamer libcamera element).

* The applications and upper level frameworks are based on the
  libcamera framework or libcamera adaptation, and are outside of
  the scope of the libcamera project.

The Pipeline Handler manages the complex pipelines exposed by the kernel
  drivers through the Media Controller and V4L2 APIs. It abstracts pipeline
  handling to hide device-specific details from the rest of the library, and
  implements both pipeline configuration based on stream configuration, and
  pipeline runtime execution and scheduling when needed by the device.

  The Pipeline Handler lives in the same process as the rest of the library, and
  has access to all helpers and kernel camera-related devices.

  Hardware abstraction is handled by device specific Pipeline Handlers which are
  derived from the Pipeline Handler base class allowing commonality to be shared
  among the implementations.

  Derived pipeline handlers create Camera device instances based on the devices
  they detect and support on the running system, and are responsible for
  managing the interactions with a camera device.
