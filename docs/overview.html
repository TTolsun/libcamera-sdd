src/libcamera/camera_manager.cpp의 CameraManager에서 시작해 요청 제출과 완료를 따라가세요.

이 문서의 용어: IPA, Pipeline Handler
  • IPA (Image Processing Algorithms): 화질 알고리즘을 담은 별도 모듈(.so)입니다. ISP가 보낸 통계를 보고 다음 프레임에 쓸 ISP 설정값을 계산합니다. 제조사가 소스를 공개하지 않고 제공할 수 있도록 libcamera 본체와 분리되어 있습니다.
  • Pipeline Handler: 특정 하드웨어 플랫폼(IPU3, RKISP1 등)의 미디어 장치를 찾아 카메라를 만들고, 요청을 장치에 넣고 완료를 돌려주는 libcamera 구성 요소입니다. 플랫폼마다 하나씩 있습니다.

다른 용어는 용어집에서 찾을 수 있습니다.

탐색과 파이프라인 선택

CameraManager는 libcamera의 진입점으로, 장치를 열거하고 애플리케이션에 시스템의 카메라 접근을 제공하는 역할을 합니다. 소개 주석에 따르면 CameraManager는 모든 Camera 객체를 소유하며, 핫플러그와 핫언플러그를 처리해 카메라의 수명을 관리합니다. CameraManager::Private::pipelineFactoryMatch는 주어진 팩토리로 PipelineHandler를 반복해서 생성하고, 각 객체의 match(enumerator_.get())가 참을 반환하는 동안 매칭되는 파이프라인을 가능한 한 많이 제공합니다. match가 거짓을 반환하면 반복을 멈추고, 매칭에 성공한 경우에만 Debug 로그를 남깁니다.

CameraManager::start()가 성공하면 시작 과정에서 열거된 시스템의 카메라를 애플리케이션이 나열하고 사용할 수 있으며, 이 상태는 카메라 매니저가 중지되거나 카메라가 시스템에서 분리될 때까지 계속됩니다. CameraManager::cameras()와 CameraManager::get()은 카메라 매니저가 실행 중인 상태에서 호출해야 하며, 이 상태를 확보할 책임은 호출하는 쪽에 있습니다.

match()를 구현하는 쪽은 필요한 장치를 모두 찾으면 MediaDevice::acquire()로 해당 장치를 모두 획득해야 합니다. 이어서 Camera 인스턴스를 생성해 내부에 저장하고 카메라 관리자에 등록한 뒤 true를 반환해야 합니다. 필요한 장치를 모두 찾지 못하면 어떤 장치도 획득하지 않거나, 이미 획득한 장치를 MediaDevice::release()로 모두 해제한 뒤 false를 반환해야 합니다.

컴포넌트별 책임

Camera 클래스는 하나의 이미지 소스에서 하나 이상의 이미지 스트림을 만들 수 있는 카메라를 나타냅니다. 장치를 구성하고 제어하며 이미지 스트림을 캡처하는 주요 인터페이스를 제공하고, libcamera가 외부에 노출하는 중심 객체입니다.

libcamera는 Camera 인스턴스의 수명을 std::shared_ptr<>로 관리합니다. 인스턴스는 create() 함수로 생성해야 하며, 이 함수는 공유 포인터를 반환합니다. Camera의 생성자와 소멸자는 private으로 선언되어 있어서, 인스턴스를 직접 생성하거나 파괴할 수 없습니다.

요청 생성과 소유권

Camera::createRequest의 cookie는 애플리케이션용 불투명 입력 값입니다. 이 값은 생성된 요청에 저장되며, Request::cookie()로 언제든지 다시 읽을 수 있습니다. 소스 설명에 따르면 애플리케이션은 보통 완료 핸들러에서 이 값으로 요청을 외부 리소스와 연결하며, libcamera 입장에서 cookie는 completely opaque(완전히 불투명)한 값입니다. Camera::createRequest()는 카메라가 Configured 또는 Running 상태일 때만 호출할 수 있으며, 오류가 발생하면 nullptr을 반환합니다.

Camera::createRequest()가 반환한 요청의 소유권은 호출자에게 넘어가며, 그 요청을 삭제할 책임도 호출자에게 있습니다. 새 요청을 만드는 대신 같은 요청을 다시 큐에 넣으려면, 호출자는 큐에 넣기 전에 Request::reuse()를 호출해서 요청의 상태와 연결된 컨트롤을 초기화해야 합니다. Request::reuse(ReuseFlag)는 flags & ReuseBuffers가 참이면 bufferMap_의 각 버퍼에 setRequest(this)를 호출하고 _d()->pending_에 넣어, addBuffer()로 이미 추가한 버퍼를 유지한 채 재사용합니다. ReuseBuffers를 지정하지 않으면 bufferMap_을 비웁니다.

캡처 세션의 상태와 자원

캡처를 준비하려면 애플리케이션은 acquire()로 카메라를 획득한 뒤 configure()로 구성하고, 그다음 start()로 시작하는 순서로 진행해야 합니다. 시작된 카메라는 정지되기 전까지 요청을 처리할 수 있으며, 이 구간이 Running 상태입니다. 완전히 끝내는 경로는 Running에서 stop()으로 Stopping을 거쳐 정지 후 Configured로 돌아가고, 이어서 Configured에서 release()로 Available로 해제하는 순서입니다. 카메라가 해제되지 않은 동안에는 애플리케이션이 시작과 정지를 여러 번 반복할 수 있으며, 카메라를 재구성하여 캡처 설정을 바꿀 수도 있습니다.

요청 제출과 완료

애플리케이션은 Camera::queueRequest()로 제출하기 전에 createRequest()가 반환한 요청 객체에 캡처 버퍼를 최소 한 개 연결해야 합니다. Camera::queueRequest()로 제출한 요청이 처리를 마치면, 카메라는 requestCompleted 신호로 완료를 알립니다. Camera::queueRequest()는 카메라가 camera_operation에 정의된 Running 상태일 때만 호출할 수 있습니다.

버퍼 완료와 요청 완료

파이프라인 핸들러는 요청의 버퍼 한 개가 완료되었음을 알리기 위해 PipelineHandler::completeBuffer()를 호출해야 합니다. completeBuffer()는 애플리케이션에 버퍼 완료를 통지하고, 요청의 내부 버퍼 추적 상태를 갱신합니다. 요청에 포함된 모든 버퍼가 완료되었으면 true를 반환하고, 그렇지 않으면 false를 반환합니다. 마지막 버퍼가 완료된 뒤에도 파이프라인 핸들러는 completeRequest()를 명시적으로 호출해야 합니다.

스레드 경계와 동기화

Camera 상태를 바꾸는 함수들은 Camera 클래스가 일반적으로 서로 동기화하지 않으므로, 필요한 경우 호출자가 이 함수들 사이의 동기화를 보장해야 합니다. PipelineHandler::completeRequest()의 호출 주체는 pipeline handler입니다. pipeline handler는 완료된 요청을 카메라에 알릴 때 이 함수를 호출해야 하며, 그 호출은 CameraManager 스레드에서 이루어져야 합니다.

정적 근거의 확인 범위

Camera::start()는 d->isAccessAllowed(Private::CameraConfigured)로 카메라 상태를 검사하고 그 반환값을 ret에 저장합니다. ret가 음수이면(ret < 0) start()는 return ret;으로 그 값을 그대로 반환하며, 이 분기에서는 파이프라인 시작 호출과 Private::CameraRunning 상태 전환이 실행되지 않습니다. API 주석의 -EACCES는 카메라가 시작할 수 없는 상태를 뜻하지만, 이 코드 조각만으로는 isAccessAllowed()가 -EACCES를 반환하는지 확인할 수 없으므로 두 값을 같은 것으로 단정하지 않습니다. 이 TODO 주석이 문서화를 요청한 대상은 카메라 시작 타이밍입니다.
