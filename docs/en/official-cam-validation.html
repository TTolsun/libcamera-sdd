Terms in this document: WSL, WSL2, NV12, metadata, and 7 others
  • WSL (Windows Subsystem for Linux): A Windows feature that allows a Linux environment to run on a Windows computer.
  • WSL2 (Windows Subsystem for Linux 2): an environment for running Linux on Windows. This site is built from libcamera compiled and extracted in WSL2.
  • NV12 (NV12): The format is 4:2:0 and uses 8 bits per component. The first plane is luminance (Y), and the second plane contains interleaved chroma data in which Cb and Cr values are stored alternately, one at a time, and the whole is placed in linearly contiguous memory.
  • Metadata: Capture information checked alongside image pixels. Request metadata is provided as a ControlList, and FrameMetadata in FrameBuffer contains the capture status, timestamps, the number of bytes used, and so on. Whether the other fields of FrameMetadata are valid depends on the capture status.
  • ISP (Image Signal Processor): the processing unit that turns the sensor's raw (bayer) data into a usable image. It performs black-level correction, lens shading correction, white balance, debayering and more.
  • DMA (Direct Memory Access): DMA(Direct Memory Access) is a term that refers to a method by which an I/O device directly reads from or writes to system memory.
  • UDMABUF (userspace dmabuf misc driver): The name of a Linux kernel driver that converts a memfd region in user space into a dma-buf.
  • VM (Virtual Machine): A virtual machine is a computer implemented in software by virtualizing the resources of a physical computer, and it runs its own operating system and applications. This is not limited to cloud servers, and it can also be created on a personal physical computer.
  • PR (Pull Request): A request proposing that code changes be merged into a project.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • GDB (GNU Project Debugger): A GNU debugger that stops a program under specified conditions and lets you examine its execution state after it stops.

Once the allocator was prepared, the official cam capture completed.

In this baseline reproduction, the default WSL kernel did not expose a DMA-BUF allocator, so the official cam could not allocate buffers.

The unmodified official cam (source commit 293d751a) was run independently three times, in three separate processes, on the recorded WSL2 trial kernel with the Virtual2 400x300 NV12 virtual camera configuration. In each run, normal completion of three frames and successful udmabuf allocation were observed. CPU-access success from the separate DMA-BUF probe was recorded separately from this cam allocation observation. The trial ended with the default kernel restored, so this configuration cannot be rerun as-is in the current state.

Virtual video also requires actual buffers: through Camera::exportFrameBuffers, PipelineHandlerVirtual::exportFrameBuffers allocates DMA-BUF buffers, and cam attaches them to Request. On the selected NV12 path, TestPatternGenerator::generateFrame uses a write-direction DmaSyncer and a write mapping. After that, the CPU converts the pattern to NV12 and writes it into the buffer.

Virtual camera requests are forwarded asynchronously from queueRequestDevice, and VirtualCameraData::processRequest waits until the target time before it attempts to generate the test pattern. If pattern generation fails, FrameError is recorded in the frame metadata status of the buffer, and buffer completion alone does not establish success. completeBuffer returns a boolean indicating whether all buffers in the request have completed, and completeRequest is called only when that boolean is true. A completed request whose notification turn has come is delivered to the cam callback connected to the requestCompleted signal. If an earlier request is still incomplete, notification of later requests is held. Because this is software processing in the virtual video path, it does not mean verification of physical sensors, ISP, or hardware DMA, nor a guarantee of exact execution timing or performance.

cam receives the completion notification and processes the frame in the event loop.

The completion notification (requestComplete) is a separate step from follow-up frame handling in the camera session (processRequest). requestComplete returns immediately if the request status is Request::RequestCancelled; otherwise, it defers processRequest to the event loop using callLater. The comment states that this deferral is meant to avoid blocking the camera manager thread.

CameraSession::processRequest compares the processed frame count captureCount_ with the configured limit captureLimit_; if a limit exists and has already been reached, it returns immediately without emitting the signal again. Otherwise, sink processing is performed only when a sink exists, while frame information output and the increment of captureCount_ proceed regardless of whether a sink exists. When the incremented captureCount_ reaches the limit, it emits the capture-done signal captureDone and returns; this signal is different from the request-completion notification.

When the processing end condition is not met (including when no limit is set) and the sink holds the request in processRequest, resubmission is deferred to later completion handling. If the sink does not hold the request, request->reuse(Request::ReuseBuffers) keeps the buffers so the request can be reused, and then an attempt to resubmit the request is made via queueRequest. CameraSession::queueRequest compares the submission count queueCount_, not the processed-frame count captureCount_, against the same captureLimit_ limit, and returns 0 without actually queueing when the submission count has already reached that limit.

In this run, the callback (requestComplete) and the follow-up processing (processRequest) were observed on different threads, but this observation does not guarantee the thread placement of every run. The cancellation branch (Request::RequestCancelled) of requestComplete exists in the source, but it was not exercised dynamically in this run.

We reproduce after confirming a supported kernel and device access.

  1. The developer investigates the Kconfig and dependent symbols of the selected kernel. The developer prioritizes investigation that does not change host state and does not affect the existing WSL/Docker.

  2. The developer directly investigates the modules actually available in the selected kernel. Because UDMABUF is not a module, it is confirmed as built in only when enabled in that kernel configuration. Adding a distribution to an existing WSL alone does not isolate the shared kernel.

  3. Based on the results of investigating kernel configuration, dependencies, actually usable modules, and allocator candidates, the developer selects one DMA-BUF allocator. To reproduce the run recorded in this document as-is, the udmabuf condition must be met. A test that selects a different allocator is distinguished from a same-condition reproduction of this recorded procedure.

  4. If shared kernel, module, .wslconfig changes, or distribution or VM shutdown is required, you must write the impact, backup path, and recovery plan, and you must obtain separate approval immediately before executing the host change. PR merge or Pages deployment approval does not replace this host change approval. Docker is stopped only when the approved plan requires stopping it.

  5. Under the approved host change plan, the developer installs and boots the recorded trial kernel 6.18.33.2-microsoft-standard-WSL2-issue211.

  6. The developer checks the recorded test conditions against the actual state before execution. The running kernel version is checked against 6.18.33.2-microsoft-standard-WSL2-issue211, the permission to open /dev/udmabuf from the root child context is checked against the recorded state, and the camera configuration is checked against Virtual2, 400x300, and NV12. All three conditions must match, and if any one differs, capture is not performed.

  7. When the execution conditions are met, the developer uses observation tools to run the unmodified official cam debug build, following the linked reproduction guide.

# Virtual Pipeline Handler

Virtual pipeline handler emulates fake external camera(s) for testing.

## Parse config file and register cameras

- A sample config file is located at `src/libcamera/pipeline/virtual/data/virtual.yaml`.
- If libcamera is installed, the config file should be installed at

### Config File Format

The config file contains the information about cameras' properties to register.
The config file should be a yaml file with dictionary of the cameraIds
associated with their properties as top level. The default value will be applied
when any property is empty.

Each camera block is a dictionary, containing the following keys:
- `supported_formats` (list of `VirtualCameraData::Resolution`, optional):
  List of supported resolution and frame rates of the emulated camera
    - `width` (`unsigned int`, default=1920): Width of the window resolution.
      This needs to be even.
    - `height` (`unsigned int`, default=1080): Height of the window resolution.
    - `frame_rates` (list of `int`, default=`[30,60]` ): Range of the frame
      rate (per second). If the list contains one value, it's the lower bound
      and the upper bound. If the list contains two values, the first is the
      lower bound and the second is the upper bound. No other number of values
      is allowed.
- `test_pattern` (`string`): Which test pattern to use as frames. The options
  are "bars", "lines". Cannot be set with `frames`.
  - The test patterns are "bars" which means color bars, and "lines" which means
    diagonal lines.
- `frames` (dictionary):
  - `path` (`string`): Path to an image, or path to a directory of a series of
    images. Cannot be set with `test_pattern`.
    - The path to an image has ".jpg" extension.
    - The path to a directory ends with "/". The name of the images in the

void CameraSession::processRequest(Request *request)
{
    /*
     * If we've reached the capture limit, we're done. This doesn't
     * duplicate the check below that emits the captureDone signal, as this
     * function will be called for each request still in flight after the
     * capture limit is reached and we don't want to emit the signal every
     * single time.
     */
    if (captureLimit_ && captureCount_ >= captureLimit_)
        return;

    const Request::BufferMap &buffers = request->buffers();

    /*
     * Compute the frame rate. The timestamp is arbitrarily retrieved from
     * the first buffer, as all buffers should have matching timestamps.
     */
    uint64_t ts = buffers.begin()->second->metadata().timestamp;
    double fps = ts - last_;
    fps = last_ != 0 && fps ? 1000000000.0 / fps : 0.0;
    last_ = ts;

    std::stringstream info;
    info << ts / 1000000000 << "."
         << std::setw(6) << std::setfill('0') << ts / 1000 % 1000000
         << " (" << std::fixed << std::setprecision(2) << fps << " fps)";

    for (const auto &[stream, buffer] : buffers) {
        const FrameMetadata &metadata = buffer->metadata();

        info << " " << streamNames_[stream]
             << " seq: " << std::setw(6) << std::setfill('0') << metadata.sequence
             << " bytesused: ";

        unsigned int nplane = 0;
        for (const FrameMetadata::Plane &plane : metadata.planes()) {
            info << plane.bytesused;
            if (++nplane < metadata.planes().size())
                info << "/";
        }
    }

    if (sink_) {
        if (!sink_->processRequest(request))
            requeue = false;
    }

    std::cout << info.str() << std::endl;

    if (printMetadata_) {
        const ControlList &requestMetadata = request->metadata();
        for (const auto &[key, value] : requestMetadata) {
            const ControlId *id = controls::controls.at(key);
            std::cout << "\t" << id->name() << " = "
                  << value.toString() << std::endl;
        }
    }

     * Notify the user that capture is complete if the limit has just been
     * reached.

    captureCount_++;
    if (captureLimit_ && captureCount_ >= captureLimit_) {
        captureDone.emit();
        return;
