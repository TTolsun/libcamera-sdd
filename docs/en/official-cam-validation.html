Terms in this document: WSL, Pipeline Handler, WSL2, NV12, and 5 others
  • WSL (Windows Subsystem for Linux): A Windows feature that allows a Linux environment to run on a Windows computer.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • WSL2 (Windows Subsystem for Linux 2): an environment for running Linux on Windows. This site is built from libcamera compiled and extracted in WSL2.
  • NV12 (NV12): The format is 4:2:0 and uses 8 bits per component. The first plane is luminance (Y), and the second plane contains interleaved chroma data in which Cb and Cr values are stored alternately, one at a time, and the whole is placed in linearly contiguous memory.
  • Metadata: Capture information checked alongside image pixels. Request metadata is provided as a ControlList, and FrameMetadata in FrameBuffer contains the capture status, timestamps, the number of bytes used, and so on. Whether the other fields of FrameMetadata are valid depends on the capture status.
  • PR (Pull Request): A request proposing that code changes be merged into a project.
  • DMA (Direct Memory Access): DMA(Direct Memory Access) is a term that refers to a method by which an I/O device directly reads from or writes to system memory.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • GDB (GNU Project Debugger): A GNU debugger that stops a program under specified conditions and lets you examine its execution state after it stops.

Once the allocator was prepared, the official cam capture completed.

In this baseline reproduction, the default WSL kernel did not expose a DMA-BUF allocator, so the official cam could not allocate buffers.

The unmodified official cam (source commit 293d751a) was run independently three times, in three separate processes, on the recorded WSL2 trial kernel with the Virtual2 400x300 NV12 virtual camera configuration. In each run, normal completion of three frames and successful udmabuf allocation were observed. CPU-access success from the separate DMA-BUF probe was recorded separately from this cam allocation observation. The trial ended with the default kernel restored, so this configuration cannot be rerun as-is in the current state.

The virtual pipeline produces video and notifies request completion.

The virtual pipeline handler, analyzed from the pinned libcamera source, emulates a virtual camera for testing and, instead of a real sensor, supports software test patterns or image input as video. The Virtual2 configuration selected this time is an example that supplies a 400x300 lines pattern, and this one configuration does not determine the entire virtual feature. After allocation succeeds, cam attaches actual DMA-BUF buffers to requests to prepare request delivery. This is the path in which, during software request processing, the CPU attempts both NV12 conversion and writes to the mapped buffer.

The pattern generator first opens a write-direction synchronization scope, and then attempts to map the buffer for writing within that scope.

Virtual requests are delivered asynchronously through a queue, and VirtualCameraData::processRequest waits until the target time before attempting pattern generation. If generation fails, the FrameError status is recorded in the frame metadata of that buffer. Whether frame generation succeeded cannot be determined solely from receiving a buffer completion signal, and the return value of completeBuffer is a boolean indicating whether all buffers of the request have completed; completeRequest is called only when this return value is true. Completed requests are delivered in submission order to the cam callback connected to the requestCompleted signal, and when an earlier request is incomplete, notification of later requests is held.

cam receives the completion notification and processes the frame in the event loop.

CameraSession::requestComplete returns without any processing if the request status is Request::RequestCancelled. For any other request, the CameraSession::processRequest call is deferred to the event loop through EventLoop::instance()->callLater. The reason is to avoid blocking the camera manager thread by handing processing of completed requests to the event loop. The source comment states this purpose explicitly.

These three actual run commands did not request display or file output options. Behavior with other selected output options was not verified by these runs. When processRequest arrives while a processing limit is set and the processed count has already reached that limit, the return is immediate, captureDone is not emitted again, and subsequent frame processing is skipped.

processRequest prints the frame information and increments the processed count by one. Then, when the processed count reaches the configured capture limit, processRequest emits the captureDone signal and returns from the function. If no processing limit is set, or if the processed count has not yet reached the limit, processRequest keeps the buffers, reuses the request, and calls the queueRequest submission helper. However, the actual submission may be skipped according to the helper's separate limit check.

The processed count and the submission attempt count are each compared against the same capture limit value. If a limit is set and the submission attempt count has already reached that limit, queueRequest skips this submission. The two checks differ in the value being counted and the timing of the check; the limit value is the same.

In this run, the request completion callback thread and the subsequent processRequest processing thread were different. However, this thread placement is not guaranteed in every run, and the RequestCancelled cancellation branch of requestComplete exists in the source but was not tested dynamically in this run.

We reproduce after confirming a supported kernel and device access.

  1. Without changing host state, investigate the Kconfig and dependency conditions of the kernel to be used.

  2. Investigate the modules the kernel to be used supports, and confirm they are actually usable. Do not treat adding a WSL distribution as isolating the kernel; assume the kernel is shared.

  3. Select one DMA-BUF allocator that matches the kernel investigation results. To reproduce under the same conditions as this record, require udmabuf.

  4. Run the host change plan, including the change proposal, kernel image hash, impact, backup, and recovery procedure, only after obtaining separate approval immediately before execution. Do not treat approval of an existing PR merge or Pages deployment as approval for this host change.

  5. After host approval, install the test kernel image according to the approved plan, and boot the test kernel using the boot procedure written in the plan.

  6. Check that the running kernel version matches the recorded 6.18.33.2-microsoft-standard-WSL2-issue211. If the versions differ, do not start capture.

  7. In the root child context, verify permission to open /dev/udmabuf.

  8. Cross-check the Virtual2 YAML size 400x300 and pattern value lines as one configuration combination.

  9. Before running, verify that the camera selection argument --camera of the new cam command is Virtual2.

  10. Verify that the cam stream argument in use includes role=video,width=400,height=300,pixelformat=NV12 so that it requests 400x300 NV12.

  11. Before running, verify that the argument actually passed to the new cam is set to --capture=3. When using the run_cam.py reproduction helper, include in the same check that this argument passes through to cam, and require that the value 3 is actually applied, not merely that the argument is present. Start capture only after all preceding pre-run checks are satisfied.

  12. Separate per-run records into one new evidence location, and run the unmodified official cam as three independent processes under debugger observation.

  13. Verify the new evidence by cross-checking the new run results against one expected result combination: camera Virtual2, actually applied stream 400x300 NV12, normal 3 frames for each independent run, and exit code 0.

## 관측된 결과

## 범위와 한계

이 결과는 `simulation=true`로 로드된 가상 파이프라인 시뮬레이션 구성의 WSL 가상 카메라 범위에만 해당합니다. 시험 커널에서 성공했다고 해서 복구된 기본 커널(`6.18.33.2-microsoft-standard-WSL2`)이 지원한다는 뜻은 아닙니다. 기본 커널은 allocator를 노출하지 않았습니다. 시험 커널에서는 udmabuf이 내장이었고, 일치하는 모듈은 설치하지 않았습니다.

권한 없는 실행의 errno 13은 이번 시험 커널 실행에만 해당하며, 앞으로 모든 권한 없는 실행을 뜻하지 않습니다. `/dev/udmabuf` 권한은 root 전용 그대로 두었습니다. 복구 후 커널은 기본 커널로 돌아왔고 `.wslconfig`는 존재하지 않습니다.

GDB 중단점은 타이밍에 영향을 주므로 콜백 반환이나 타이밍·성능을 확정하는 증거가 아닙니다. 물리 DMA, 물리 카메라, 제품 앱, 사내 HAL은 검증하지 않았고, 사람 검토는 pending 상태입니다.

# Virtual Pipeline Handler

Virtual pipeline handler emulates fake external camera(s) for testing.

## Parse config file and register cameras

- A sample config file is located at `src/libcamera/pipeline/virtual/data/virtual.yaml`.
- If libcamera is installed, the config file should be installed at
  `share/libcamera/pipeline/virtual/virtual.yaml`.

### Config File Format

The config file contains the information about cameras' properties to register.
The config file should be a yaml file with dictionary of the cameraIds
associated with their properties as top level. The default value will be applied
when any property is empty.

Each camera block is a dictionary, containing the following keys:
- `supported_formats` (list of `VirtualCameraData::Resolution`, optional):
  List of supported resolution and frame rates of the emulated camera
    - `width` (`unsigned int`, default=1920): Width of the window resolution.
      This needs to be even.
    - `height` (`unsigned int`, default=1080): Height of the window resolution.
    - `frame_rates` (list of `int`, default=`[30,60]` ): Range of the frame
      rate (per second). If the list contains one value, it's the lower bound
      and the upper bound. If the list contains two values, the first is the
      lower bound and the second is the upper bound. No other number of values
      is allowed.
- `test_pattern` (`string`): Which test pattern to use as frames. The options
  are "bars", "lines". Cannot be set with `frames`.
  - The test patterns are "bars" which means color bars, and "lines" which means
    diagonal lines.
- `frames` (dictionary):
  - `path` (`string`): Path to an image, or path to a directory of a series of
    images. Cannot be set with `test_pattern`.
    - The path to an image has ".jpg" extension.
    - The path to a directory ends with "/". The name of the images in the
      directory are "{n}.jpg" with {n} is the sequence of images starting with 0.
- `location` (`string`, default="front"): The location of the camera. Support
  "Front", "Back", and "External".
- `model` (`string`, default="Unknown"): The model name of the camera.

Check `data/virtual.yaml` as the sample config file.

void VirtualCameraData::processRequest(Request *request,
                       uint64_t targetTimestamp)
{
    const auto targetTime = std::chrono::steady_clock::time_point{
        std::chrono::nanoseconds(targetTimestamp)
    };
    std::this_thread::sleep_until(targetTime);

    for (const auto &[stream, buffer] : request->buffers()) {
        bool found = false;
        /* map buffer and fill test patterns */
        for (auto &streamConfig : streamConfigs_) {
            if (stream == &streamConfig.stream) {
                FrameMetadata &fmd = buffer->_d()->metadata();

                fmd.status = FrameMetadata::Status::FrameSuccess;
                fmd.sequence = streamConfig.seq++;
                fmd.timestamp = targetTimestamp;

                std::span<const FrameBuffer::Plane> planes = buffer->planes();
                for (const auto [i, p] : utils::enumerate(planes))
                    fmd.planes()[i].bytesused = p.length;

                found = true;

                if (streamConfig.frameGenerator->generateFrame(
                        stream->configuration(), buffer))
                    fmd.status = FrameMetadata::Status::FrameError;

                bufferCompleted.emit(buffer);
                break;
            }
        }
        ASSERT(found);
    }
}

void CameraSession::processRequest(Request *request)
{
    /*
     * If we've reached the capture limit, we're done. This doesn't
     * duplicate the check below that emits the captureDone signal, as this
     * function will be called for each request still in flight after the
     * capture limit is reached and we don't want to emit the signal every
     * single time.
     */
    if (captureLimit_ && captureCount_ >= captureLimit_)
        return;

    const Request::BufferMap &buffers = request->buffers();

    /*
     * Compute the frame rate. The timestamp is arbitrarily retrieved from
     * the first buffer, as all buffers should have matching timestamps.
     */
    uint64_t ts = buffers.begin()->second->metadata().timestamp;
    double fps = ts - last_;
    fps = last_ != 0 && fps ? 1000000000.0 / fps : 0.0;
    last_ = ts;

    bool requeue = true;

    std::stringstream info;
    info << ts / 1000000000 << "."
         << std::setw(6) << std::setfill('0') << ts / 1000 % 1000000
         << " (" << std::fixed << std::setprecision(2) << fps << " fps)";

    for (const auto &[stream, buffer] : buffers) {
        const FrameMetadata &metadata = buffer->metadata();

        info << " " << streamNames_[stream]
             << " seq: " << std::setw(6) << std::setfill('0') << metadata.sequence
             << " bytesused: ";

        unsigned int nplane = 0;
        for (const FrameMetadata::Plane &plane : metadata.planes()) {
            info << plane.bytesused;
            if (++nplane < metadata.planes().size())
                info << "/";
        }
    }

    if (sink_) {
        if (!sink_->processRequest(request))
            requeue = false;
    }

    std::cout << info.str() << std::endl;

    if (printMetadata_) {
        const ControlList &requestMetadata = request->metadata();
        for (const auto &[key, value] : requestMetadata) {
            const ControlId *id = controls::controls.at(key);
            std::cout << "\t" << id->name() << " = "
                  << value.toString() << std::endl;
        }
    }

    /*
     * Notify the user that capture is complete if the limit has just been
     * reached.
     */
    captureCount_++;
    if (captureLimit_ && captureCount_ >= captureLimit_) {
        captureDone.emit();
        return;
    }

    /*
     * If the frame sink holds on the request, we'll requeue it later in the
     * complete handler.
     */
    if (!requeue)
        return;

    request->reuse(Request::ReuseBuffers);
    queueRequest(request);
}

# 공식 cam WSL 가상 카메라 검증

## 결론과 다음 행동

먼저 아래 준비 1번부터 시작합니다. 호스트 승인 전에는 Docker를 중지하거나 WSL을 종료하지 않습니다.

## 관측된 결과

소스 `293d751a814e0d4c34e85ad457ccd9d5eefd1a61`을 수정하지 않은 디버그 빌드의 공식 cam은 시험 커널 `6.18.33.2-microsoft-standard-WSL2-issue211`의 WSL `Virtual2` 카메라(400x300 NV12)에서 프레임 3개를 처리했습니다. 실행 세 개(PID 434, 449, 464)는 모두 request와 sequence 0~2에서 status 1, buffer_status 0을 기록했습니다.

세 기록은 PID, request, sequence로 묶어 status를 비교합니다. 콜백 TID(437, 452, 467)와 처리 TID(434, 449, 464)는 실행마다 달랐으므로 같아야 하는 키가 아니라 속성으로 기록합니다.

DMA 프로브는 `/dev/udmabuf` 열기, 4096바이트 할당, mmap, RW START(flags 3), CPU 접근, RW END(flags 7), munmap과 닫기를 모두 errno 0으로 마쳤습니다. 0.5초 시간 초과 시험은 시간 초과(exit 1)로 끝났고, 정리 반환 코드는 모두 0이었습니다. 반환 코드 0은 정리가 성공했다는 뜻이며, 정리 이벤트가 0개라는 뜻이 아닙니다. 없는 provider는 errno 2, 지원하지 않는 ioctl은 errno 25로 실패했습니다.

`cancelled_callbacks` 0은 세 실행 모두에서 관측된 값입니다. 다만 취소 분기를 동적으로 실행한 결과가 아니며, 0으로 강제한 값도 아닙니다.

## 범위와 한계

이 결과는 `simulation=true`로 로드된 가상 파이프라인 시뮬레이션 구성의 WSL 가상 카메라 범위에만 해당합니다. 시험 커널에서 성공했다고 해서 복구된 기본 커널(`6.18.33.2-microsoft-standard-WSL2`)이 지원한다는 뜻은 아닙니다. 기본 커널은 allocator를 노출하지 않았습니다. 시험 커널에서는 udmabuf이 내장이었고, 일치하는 모듈은 설치하지 않았습니다.

권한 없는 실행의 errno 13은 이번 시험 커널 실행에만 해당하며, 앞으로 모든 권한 없는 실행을 뜻하지 않습니다. `/dev/udmabuf` 권한은 root 전용 그대로 두었습니다. 복구 후 커널은 기본 커널로 돌아왔고 `.wslconfig`는 존재하지 않습니다.

GDB 중단점은 타이밍에 영향을 주므로 콜백 반환이나 타이밍·성능을 확정하는 증거가 아닙니다. 물리 DMA, 물리 카메라, 제품 앱, 사내 HAL은 검증하지 않았고, 사람 검토는 pending 상태입니다.

## 실행 전 준비

1. 호스트 상태를 바꾸지 않고 커널을 조사합니다. 커널 태그 `linux-msft-wsl-6.18.33.2`(commit `c21a03b2943d147c280bdf32530d4fe6badfd6bd`, 이미지 SHA-256 `cf23bf492a00a5c7517e221b0d8f742ea3cffa9351823191a5ba5c476ba15460`)의 `CONFIG_UDMABUF`, `CONFIG_DMA_SHARED_BUFFER`, `CONFIG_MEMFD_CREATE`(또는 `CONFIG_COMPILE_TEST`), `CONFIG_MMU`, 할당기 후보 `CONFIG_DMABUF_HEAPS`를 확인합니다. `CONFIG_UDMABUF`는 bool이므로 모듈이 아니라 내장 여부만 확인하고, 실제 사용 가능한 모듈과 할당기 후보를 조사한 뒤 사용할 할당기를 하나 선택합니다. `CONFIG_UDMABUF`는 테스트·디버그 용도의 기능이며, 잘못 사용하면 사용자 공간에서 커널 드라이버를 교착시킬 수 있으므로 시험 환경 밖에서 사용하지 않습니다. 기존 WSL에 배포판을 추가하는 것만으로 커널이 격리된다고 보지 않습니다. 커널 빌드 예시는 [prepare_kernel.sh](../validation/issue211/prepare_kernel.sh)이며, 실행 전 태그와 출력 위치를 확인합니다. 이 예시와 [prepare_runtime.sh](../validation/issue211/prepare_runtime.sh)는 기록된 예시이므로 로컬 경로와 설정을 현재 환경에서 다시 확인해야 하며, 실행 전 각 스크립트의 실제 동작과 입력을 직접 읽어 확인합니다. 이 예시들은 커널을 설치하거나 부팅하지 않으며, 설치와 부팅은 2단계 계획과 승인 뒤에만 수행합니다.
