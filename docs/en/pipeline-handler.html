Check the configuration, request, completion and shutdown contracts that pipeline implementations must meet.

Terms in this document: Pipeline Handler, ASSERT, IPU3
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • ASSERT: libcamera's debug check macro. In debug builds, a false condition logs a fatal message and aborts execution.
  • IPU3 (Intel Image Processing Unit 3): the camera ISP in some Intel laptop processors. libcamera has a Pipeline Handler and an IPA for it.

Other terms are in the Glossary.

Device matching and object lifetime

PipelineHandler is reference-counted through std::shared_ptr<>, must not be created manually, and must be created through PipelineHandlerFactoryBase::create(). match() must, when all devices are acquired by MediaDevice::acquire(), create Camera, register it with the camera manager, and return true; on failure, it must either acquire no device or release the acquired devices with MediaDevice::release(), and return false. Devices acquired by acquireMediaDevice() are stored in mediaDevices_, must not be released directly, and are released with MediaDevice::release() in the destructor when the handler is destroyed. acquire() locks the devices when useCount_ is 0; if the lock fails, or if acquireDevice() fails while useCount_ is 0, it unlocks them with unlockMediaDevices() and returns false. Each successful acquire() must be paired with a release(), and release() unlocks the devices when useCount_ is 1.

Configuration inputs and validation duties

In generateConfiguration(), the caller shall populate roles, the list of stream roles, with the desired use cases. This function may be called from any thread, and the implementation shall be threadsafe. The implementation shall not modify the state of the camera, and generateConfiguration() returns a valid CameraConfiguration if the requested roles can be satisfied, and returns a null pointer otherwise. configure() is called from the CameraManager thread, and its intended caller is the Camera class, which receives the configuration to apply from the application. Because the configuration is guaranteed to have been validated with CameraConfiguration::validate(), the implementation shall not perform further validation and may rely on custom fields in its custom derived class. The pipeline handler shall associate a Stream instance with each StreamConfiguration entry using StreamConfiguration::setStream(), and configure() returns 0 on success, and configure() returns a negative error code otherwise.

Stopping and outstanding requests

PipelineHandler::stop moves the contents of waitingRequests_ of camera->_d() into the local variable waitingRequests by swapping them, so waitingRequests_ is emptied after the move. According to the comment, the reason for separating them first is so that waiting requests are not requeued in response to completeRequest() being called inside stopDevice(). The device stop function called immediately afterward is stopDevice(camera).

PipelineHandler::stop() moves the waiting request queue into the local variable waitingRequests, separating it beforehand, before calling stopDevice(camera). After stopDevice(camera) returns, it takes the separated requests one by one from the front, marks each as cancelled with request->_d()->cancel(), and then calls doQueueRequest(request). To preserve the order of requests, cancellation handling is deferred until after stopDevice.

A stopDevice implementation must immediately stop capture and request processing for all running streams. Pending requests must be cancelled and immediately completed in an error state, and they must not be treated as a normal completion state. This is the contract stated in the stopDevice function documentation; it does not mean that a specific device implementation has verified this contract.

The ASSERT(data->queuedRequests_.empty()) and ASSERT(data->waitingRequests_.empty()) at the end of stop() check whether the two queues are empty. A cancelled request is passed to doQueueRequest() after request->_d()->cancel(), is temporarily added to queuedRequests_, and is completed in completeRequest(), so this check confirms the state after that processing has finished. This ASSERT only checks whether the two queues were empty during this call. It is not a guarantee that no requests remain in later executions. On the line after the check, data->requestSequence_ is initialized to 0.

On normal completion, completeRequest calls doQueueRequests(camera) last. doQueueRequests passes a request to doQueueRequest only when the front request of waitingRequests_ is prepared (prepared_) and the size of queuedRequests_ has not reached maxQueuedRequestsDevice_. Therefore, on normal completion, delivery of waiting requests is determined by three conditions: the waiting queue, the prepared state, and the device limit. A call to completeRequest does not by itself guarantee submission to the device. In contrast, stop moves waitingRequests_ into a local queue before calling stopDevice(camera). So even if completion handling inside stopDevice re-enters doQueueRequests, the original waiting requests are not submitted again.

Input Size Search Boundaries in IPU3

minIfWidth is calculated as std::max(in.width - ImgUDevice::kIFMaxCropWidth, ImgUDevice::kIFMaxCropWidth), which is the larger of the input width minus kIFMaxCropWidth and kIFMaxCropWidth. minIfHeight is calculated as std::max(in.height - ImgUDevice::kIFMaxCropHeight, ImgUDevice::kIFMaxCropHeight), which is the larger of the input height minus kIFMaxCropHeight and kIFMaxCropHeight.

The first search has the outer loop handle the width (ifWidth) and the inner loop handle the height (ifHeight), repeating while ifWidth is greater than or equal to minIfWidth and ifHeight is greater than or equal to minIfHeight, and decreasing them by kIFAlignWidth and kIFAlignHeight respectively. The second search swaps the roles, making height the outer loop and width the inner loop, and repeats under the same minimum-value conditions. Before the second search, ifWidth and ifHeight are re-initialized with alignUp, but the outer loop variable ifHeight is not re-initialized on each inner-loop iteration. The calculateBDSHeight() comment explains that it crops up to kIFMaxCropHeight lines from the input formatter height, so cropping the height below the minimum makes the minimum height wrap. The minIFHeight subtraction in calculateBDSHeight() is the boundary where the value wraps when iif.height is smaller than kIFMaxCropHeight, and this is a different calculation from the caller reducing ifHeight by kIFAlignHeight each step.

\brief Search and acquire a MediaDevice matching a device pattern
 * \param[in] enumerator Enumerator containing all media devices in the system
 * \param[in] dm Device match pattern
 *
 * Search the device \a enumerator for an available media device matching the
 * device match pattern \a dm. Matching media device that have previously been
 * acquired by MediaDevice::acquire() are not considered. If a match is found,
 * the media device is acquired and returned. The caller shall not release the
 * device explicitly, it will be automatically released when the pipeline
 * handler is destroyed.
 *
 * \context This function shall be called from the CameraManager thread.
 *
 * \return A shared pointer to the matching MediaDevice, or nullptr if no match
 * is found
 */
std::shared_ptr<MediaDevice>
PipelineHandler::acquireMediaDevice(DeviceEnumerator *enumerator,
                    const DeviceMatch &dm)
{
    std::shared_ptr<MediaDevice> media = enumerator->search(dm);
    if (!media)
        return nullptr;

    if (!media->acquire())
        return nullptr;

    mediaDevices_.push_back(media);

    return media;
}

/**
 * \brief Acquire exclusive access to the pipeline handler for the process
 *
 * This function locks all the media devices used by the pipeline to ensure
 * that no other process can access them concurrently.
 *
 * Access to a pipeline handler may be acquired recursively from within the
 * same process. Every successful acquire() call shall be matched with a
 * release() call. This allows concurrent access to the same pipeline handler
 * from different cameras within the same process.
 *
 * Pipeline handlers shall not call this function directly as the Camera class
 * handles access internally.
 *
 * \context This function is called from the CameraManager thread.
 *
 * \return True if the pipeline handler was acquired, false if another process
 * has already acquired it
 * \sa release()
 */
bool PipelineHandler::acquire(Camera *camera)
{
    if (useCount_ == 0) {
        for (std::shared_ptr<MediaDevice> &media : mediaDevices_) {
            if (!media->lock()) {
                unlockMediaDevices();
                return false;
            }
        }
    }

    if (!acquireDevice(camera)) {
        if (useCount_ == 0)
            unlockMediaDevices();

        return false;
    }

    ++useCount_;
    return true;
}

/**
 * \brief Release exclusive access to the pipeline handler
 * \param[in] camera The camera for which to release data
 *
 * This function releases access to the pipeline handler previously acquired by
 * a call to acquire(). Every release() call shall match a previous successful
 * acquire() call. Calling this function on a pipeline handler that hasn't been
 * acquired results in undefined behaviour.
 *
 * Pipeline handlers shall not call this function directly as the Camera class
 * handles access internally.
 *
 * \context This function is called from the CameraManager thread.
 *
 * \sa acquire()
 */
void PipelineHandler::release(Camera *camera)
{
    ASSERT(useCount_);

    releaseDevice(camera);

    if (useCount_ == 1)
        unlockMediaDevices();

    --useCount_;
}

\brief Stop capturing from all running streams and cancel pending requests
 * \param[in] camera The camera to stop
 *
 * This function stops capturing and processing requests immediately. All
 * pending requests are cancelled and complete immediately in an error state.
 *
 * \context This function is called from the CameraManager thread.
 */
void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());

    data->requestSequence_ = 0;
}

\brief Complete a buffer for a request
 * \param[in] request The request the buffer belongs to
 * \param[in] buffer The buffer that has completed
 *
 * This function shall be called by pipeline handlers to signal completion of
 * the \a buffer part of the \a request. It notifies applications of buffer
 * completion and updates the request's internal buffer tracking. The request
 * is not completed automatically when the last buffer completes to give

 *

bool PipelineHandler::completeBuffer(Request *request, FrameBuffer *buffer)

    return request->_d()->completeBuffer(buffer);
}

/**
 * \brief Signal request completion
 * \param[in] request The request that has completed
 *
 * The pipeline handler shall call this function to notify the \a camera that
 * the request has completed. The request is no longer managed by the pipeline
 * handler and shall not be accessed once this function returns.
 *
 * This function ensures that requests will be returned to the application in
 * submission order, the pipeline handler may call it on any complete request
 * without any ordering constraint.
 *
 * \context This function shall be called from the CameraManager thread.
 */
void PipelineHandler::completeRequest(Request *request)
{
    Camera *camera = request->_d()->camera();

    request->_d()->complete();

    Camera::Private *data = camera->_d();

    while (!data->queuedRequests_.empty()) {
        Request *req = data->queuedRequests_.front();
        if (req->status() == Request::RequestPending)
            break;

        ASSERT(!req->hasPendingBuffers());
        data->queuedRequests_.pop_front();
        camera->requestComplete(req);
    }

    /* Allow any waiting requests to be queued to the pipeline. */
    doQueueRequests(camera);
}

/**
 * \brief Cancel request and signal its completion
 * \param[in] request The request to cancel
 *
 * This function cancels and completes the request. The same rules as for
 * completeRequest() apply.
 */
void PipelineHandler::cancelRequest(Request *request)
{
    request->_d()->cancel();
    completeRequest(request);
}

void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();
    while (!data->waitingRequests_.empty()) {
        if (data->queuedRequests_.size() == maxQueuedRequestsDevice_)
            break;

        Request *request = data->waitingRequests_.front();
        if (!request->_d()->prepared_)
            break;

        /*
         * Pop the request first, in case doQueueRequests() is called
         * recursively from within doQueueRequest()
         */
        data->waitingRequests_.pop();
        doQueueRequest(request);
    }
}
