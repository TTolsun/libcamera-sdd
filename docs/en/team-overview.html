Terms in this document: V4L2, Pipeline Handler, HAL, IPA
  • V4L2 (Video4Linux2): the Linux kernel API for cameras and video devices. libcamera controls sensors and ISP devices through it.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.

Other terms are in the Glossary.

What it does

libcamera is an open-source library supporting complex cameras for Linux, Android, and ChromeOS. It connects to Linux kernel device drivers and provides developers with an intuitive API, reducing the complexity of capturing images with complex cameras on Linux systems.

Userspace is responsible for providing a working camera stack using the driver. Vendors typically implement this independently, and there is no common architecture or API for application developers. Custom handling is often needed because hardware pipelines and their representations in the kernel API differ.

libcamera provides a complete camera stack for Linux-based systems. It abstracts hardware configuration performed through kernel APIs and work related to image control algorithms to obtain the desired results from a camera, allowing developers to handle them in a simple and consistent way. The camera stack consists of four layers, from bottom to top: kernel drivers, the libcamera framework, the libcamera adaptation layer, and applications and higher-level frameworks.

Inputs

The kernel driver controls the camera hardware and provides a low-level interface to userspace through the Media Controller API, V4L2 Video Device API, and V4L2 Subdev API, which belong to the Linux kernel's V4L2 API family (interfaces through which programs interact with devices). Exactly what libcamera receives from the lower layer to control cameras has not been confirmed. The Camera Manager, the camera manager, enumerates cameras supported by libcamera and creates a Pipeline Handler to manage each camera. Only one Camera Manager runs per application, and it ensures that only one application at a time has control of a camera device.

Outputs

libcamera provides a native C++ API that allows applications to control camera devices. Optional language bindings allow other programming languages to connect to libcamera as well.

libcamera adaptations collectively refer to components that connect other frameworks to libcamera. Examples include the V4L2 compatibility layer, the libcamera element for gstreamer, and an Android camera hardware abstraction layer (HAL) implementation based on libcamera. These components may reside in separate source repositories of the libcamera project or move to the repositories of their respective projects.

Boundaries with other teams and layers

Applications (programs that users run) and upper-level frameworks (the higher-level software base that supports applications) are based on the libcamera framework or a form that applies libcamera, and are outside the scope of the libcamera project.

Device manufacturers must contribute upstream a Pipeline Handler that is part of the libcamera codebase. The Pipeline Handler configures the device's camera processing path based on stream settings, manages execution and scheduling when needed, creates Camera instances, and handles interactions with the device. Device manufacturers may separately provide an IPA Module that runs algorithms such as auto exposure, auto white balance, and auto focus on the CPU and controls hardware image processing according to parameters from higher layers. IPA Module included in libcamera are subject to free software licenses, and external modules may be distributed under closed-source licenses if they do not contain source code from the libcamera project.

The camera stack comprises four software layers. From bottom to top:

* The kernel drivers control the camera hardware and expose a
  low-level interface to userspace through the Linux kernel V4L2
  family of APIs (Media Controller API, V4L2 Video Device API and
  V4L2 Subdev API).

* The libcamera framework is the core part of the stack. It
  handles all control of the camera devices in its core component,
  libcamera, and exposes a native C++ API to upper layers. Optional
  language bindings allow interfacing to libcamera from other
  programming languages.

  Those components live in the same source code repository and
  all together constitute the libcamera framework.

* The libcamera adaptation is an umbrella term designating the
  components that interface to libcamera in other frameworks.
  Notable examples are a V4L2 compatibility layer, a gstreamer
  libcamera element, and an Android camera HAL implementation based
  on libcamera.

  Those components can live in the libcamera project source code
  in separate repositories, or move to their respective project's
  repository (for instance the gstreamer libcamera element).

* The applications and upper level frameworks are based on the
  libcamera framework or libcamera adaptation, and are outside of
  the scope of the libcamera project.

The Pipeline Handler manages the complex pipelines exposed by the kernel
  drivers through the Media Controller and V4L2 APIs. It abstracts pipeline
  handling to hide device-specific details from the rest of the library, and
  implements both pipeline configuration based on stream configuration, and
  pipeline runtime execution and scheduling when needed by the device.

  The Pipeline Handler lives in the same process as the rest of the library, and
  has access to all helpers and kernel camera-related devices.

  Hardware abstraction is handled by device specific Pipeline Handlers which are
  derived from the Pipeline Handler base class allowing commonality to be shared
  among the implementations.

  Derived pipeline handlers create Camera device instances based on the devices
  they detect and support on the running system, and are responsible for
  managing the interactions with a camera device.
