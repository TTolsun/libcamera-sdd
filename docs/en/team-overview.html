Briefly check what this project takes in and what it puts out, and which layers and teams it touches.

Terms in this document: V4L2, HAL, Pipeline Handler, IPA
  • V4L2 (Video4Linux2): the Linux kernel API for cameras and video devices. libcamera controls sensors and ISP devices through it.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.

Other terms are in the Glossary.

What it does

libcamera is an open-source library that supports complex cameras for Linux, Android, and ChromeOS. It interfaces with Linux kernel device drivers and provides developers with an intuitive API, reducing the complexity of capturing images with complex cameras on Linux systems.

At the bottom, kernel drivers control camera hardware and provide a low-level interface to userspace through the Linux kernel's V4L2 API. Above them, the libcamera framework uses its core component, libcamera, to control camera devices and provide a C++ API to higher layers; optional language bindings allow it to connect to other programming languages. The next layer, the libcamera adaptation layer, refers to components that connect other frameworks to libcamera, such as the V4L2 compatibility layer, the gstreamer libcamera element, and the Android camera HAL implementation. Applications and higher-level frameworks at the top are based on the libcamera framework or the adaptation layer and are outside the scope of the libcamera project.

Inputs

The kernel driver controls the camera hardware and provides userspace with low-level interfaces close to the hardware through the Media Controller API, V4L2 Video Device API, and V4L2 Subdev API, which are part of the Linux kernel's V4L2 API family. What this project receives from the lower layer to control the camera has not been confirmed. The Camera Manager, the component that finds and manages cameras, enumerates cameras and creates a Pipeline Handler, the component responsible for camera processing, to manage each Camera supported by libcamera. Only one Camera Manager instance runs per application, ensuring that only one application at a time can control a camera device.

Boundaries with other teams and layers

Applications and higher-level frameworks based on the libcamera framework (the basic structure of the software) or on an adaptation of libcamera for another environment are outside the scope of the libcamera project. Device manufacturers must contribute device-specific Pipeline Handlers that manage interactions with camera devices directly to libcamera. IPA, an image processing algorithm, is provided as an external plugin called an IPA Module and may be supplied separately by camera manufacturers. IPA Modules included in libcamera are subject to free software licenses, and externally developed IPA Modules may be distributed under closed-source licenses if they do not include libcamera project source code.

The camera stack comprises four software layers. From bottom to top:

* The kernel drivers control the camera hardware and expose a
  low-level interface to userspace through the Linux kernel V4L2
  family of APIs (Media Controller API, V4L2 Video Device API and
  V4L2 Subdev API).

* The libcamera framework is the core part of the stack. It
  handles all control of the camera devices in its core component,
  libcamera, and exposes a native C++ API to upper layers. Optional
  language bindings allow interfacing to libcamera from other
  programming languages.

  Those components live in the same source code repository and
  all together constitute the libcamera framework.

* The libcamera adaptation is an umbrella term designating the
  components that interface to libcamera in other frameworks.
  Notable examples are a V4L2 compatibility layer, a gstreamer
  libcamera element, and an Android camera HAL implementation based
  on libcamera.

  Those components can live in the libcamera project source code
  in separate repositories, or move to their respective project's
  repository (for instance the gstreamer libcamera element).

* The applications and upper level frameworks are based on the
  libcamera framework or libcamera adaptation, and are outside of
  the scope of the libcamera project.

The Pipeline Handler manages the complex pipelines exposed by the kernel
  drivers through the Media Controller and V4L2 APIs. It abstracts pipeline
  handling to hide device-specific details from the rest of the library, and
  implements both pipeline configuration based on stream configuration, and
  pipeline runtime execution and scheduling when needed by the device.

  The Pipeline Handler lives in the same process as the rest of the library, and
  has access to all helpers and kernel camera-related devices.

  Hardware abstraction is handled by device specific Pipeline Handlers which are
  derived from the Pipeline Handler base class allowing commonality to be shared
  among the implementations.

  Derived pipeline handlers create Camera device instances based on the devices
  they detect and support on the running system, and are responsible for
  managing the interactions with a camera device.
