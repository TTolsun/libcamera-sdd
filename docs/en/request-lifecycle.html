Distinguish successful request submission from capture completion, and check how long buffers must remain valid and where a failure occurred.

Terms in this document: fence, Pipeline Handler, Pending, Metadata, and 2 others
  • fence: A synchronization signal indicating when a buffer can be used. A request with a valid fence waits for the signal during preparation. This is different from request completion.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • Pending: A request state that has not yet changed to complete or cancelled. It does not mean device processing has started; an earlier request in this state can delay later returns.
  • Metadata: Capture information checked alongside image pixels. Request metadata is provided as a ControlList, and FrameMetadata in FrameBuffer contains the capture status, timestamps, the number of bytes used, and so on. Whether the other fields of FrameMetadata are valid depends on the capture status.
  • errno: the standard error numbers Linux functions use to report why they failed. libcamera functions return them as negative values. For example, -ENODEV means no device, -EACCES access denied, -EINVAL an invalid argument, -ENOMEM out of memory and -EXDEV a resource that belongs to another object.
  • ASSERT: libcamera's debug check macro. In debug builds, a false condition logs a fatal message and aborts execution.

Other terms are in the Glossary.

If Camera::queueRequest returns 0, the request was successfully queued. After the request is queued, the camera signals its completion with requestCompleted. waitingRequests_ holds requests waiting to become ready; if the request at the front is not ready, it does not forward subsequent requests to the device. maxQueuedRequestsDevice_ is the limit on the number of requests queued to the device. If the size of queuedRequests_ equals this value, forwarding of pending requests stops.

The member that indicates whether the leading request is ready is prepared_; if its value is false, the loop exits. doQueueRequest calls the tracepoint, adds the request to queuedRequests_, and then assigns a sequence number. If cancelled_ is true, doQueueRequest calls completeRequest and exits. Otherwise, doQueueRequest calls queueRequestDevice, and if queueRequestDevice returns a nonzero value, doQueueRequest calls cancelRequest.

The function is named PipelineHandler::queueRequestDevice() and returns 0 on success. If an error occurs, the function returns a negative error code. The pipeline handler must call completeBuffer() on the CameraManager thread to signal completion of a buffer in the request. Even when the last buffer is completed, the request is not completed automatically, so the pipeline handler must explicitly call completeRequest().

Even when the last buffer completes, the request does not complete automatically, so the pipeline handler must explicitly complete the request by calling completeRequest(). After marking the request as complete, completeRequest checks requests starting from the front of queuedRequests_. If the status of the request at the front is RequestPending, the function stops iterating and does not check the requests behind it. Otherwise, the function verifies that no buffers are pending, removes the request from the queue, and calls requestComplete() to return the request to the application in submission order.

If the request's status is Request::RequestPending, iteration stops.

Request, buffer and fence lifetimes

Ownership of the request returned by Camera::createRequest() passes to the caller, who is responsible for deleting it. The caller may delete the request in the completion handler or reset its state with Request::reuse() and reuse it. Request::addBuffer() stores a reference to the buffer in the request. The caller must ensure that the buffer remains valid until the request completion callback is called.

How long to retain requests and buffers

The caller owns the request. Attaching a buffer reference preserves the caller's responsibility to keep the buffer valid.

If Request::addBuffer() succeeds, ownership of the valid Fence passed to it transfers to the destination buffer, buffer. If Request::addBuffer() fails, it does not take ownership of the fence passed to it and leaves its state unchanged. If the fence associated with the buffer is not signaled, the request fails after a timeout, and the fence remains attached to the buffer. The application must retrieve the fence using FrameBuffer::releaseFence() before reusing this buffer in another request.

If ReuseBuffers is set in flags, Request::reuse() calls buffer->_d()->setRequest(this) for each buffer in bufferMap_ to associate the buffer with the current request. If ReuseBuffers is present in flags, Request::reuse() sets the current request on each existing buffer in bufferMap_ and then adds that buffer to pending_. If ReuseBuffers is absent from flags, Request::reuse() calls bufferMap_.clear() to clear bufferMap_. This assignment in Request::reuse stores the RequestPending state in status_.

Request::reuse calls controls_.clear() to clear controls_. Request::reuse calls metadata_'s clear() to clear the metadata. The Request::ReuseBuffers flag preserves buffers previously added with addBuffer() for reuse. Fences associated with the buffers are not reused.

When using fences, it is recommended not to use the Request::ReuseBuffers flag. cancelRequest completes the request by calling completeRequest after cancelling it, and the same rules as completeRequest apply. Whichever function the pipeline handler calls, the pipeline handler must not access the request after that function returns. At that point, the pipeline handler no longer manages the request.

Change review and runtime checks

We propose recording the return value of queueRequest: 0 on success or a negative error code on failure. The error code may be -ENODEV, -EACCES, -EXDEV, -EINVAL, or -ENOMEM. The variable being assigned is status_. We also propose recording the value of status_ before and after the assignment in Request::reuse(), along with the RequestPending being assigned.

We propose recording controls_, the target variable of the clear call. We propose including metadata_, the target variable of the clear call, in the recorded items. We propose recording the return value of req->status(), the status query expression for the leading request. We propose recording whether the stopDevice(camera) call site was reached in PipelineHandler::stop.

\brief Queue a request to the camera
 * \param[in] request The request to queue to the camera
 *
 * This function queues a \a request to the camera for capture.
 *
 * After allocating the request with createRequest(), the application shall
 * fill it with at least one capture buffer before queuing it. Requests that
 * contain no buffers are invalid and are rejected without being queued.
 *
 * Once the request has been queued, the camera will notify its completion
 * through the \ref requestCompleted signal.
 *
 * \context This function is \threadsafe. It may only be called when the camera
 * is in the Running state as defined in \ref camera_operation.
 *
 * \return 0 on success or a negative error code otherwise
 * \retval -ENODEV The camera has been disconnected from the system
 * \retval -EACCES The camera is not running so requests can't be queued
 * \retval -EXDEV The request does not belong to this camera
 * \retval -EINVAL The request is invalid
 * \retval -ENOMEM No buffer memory was available to handle the request
 */
int Camera::queueRequest(Request *request)
{
    Private *const d = _d();

    int ret = d->isAccessAllowed(Private::CameraRunning);
    if (ret < 0)
        return ret;

    /* Requests can only be queued to the camera that created them. */
    if (request->_d()->camera() != this) {
        LOG(Camera, Error) << "Request was not created by this camera";
        return -EXDEV;
    }

    if (request->status() != Request::RequestPending) {
        LOG(Camera, Error) << request->toString() << " is not valid";
        return -EINVAL;
    }

    /* Make sure the Request has a valid control list. */
    if (request->controls().infoMap() != &controls()) {
        LOG(Camera, Error) << "Overwriting Request::controls() is not allowed";
        return -EINVAL;
    }

    /*
     * The camera state may change until the end of the function. No locking
     * is however needed as PipelineHandler::queueRequest() will handle
     * this.
     */

    if (request->buffers().empty()) {
        LOG(Camera, Error) << "Request contains no buffers";
        return -EINVAL;
    }

    for (const auto &[stream, buffer] : request->buffers()) {
        if (d->activeStreams_.find(stream) == d->activeStreams_.end()) {
            LOG(Camera, Error) << "Invalid request";
            return -EINVAL;
        }
    }

    /* Pre-process AeEnable. */
    patchControlList(request->controls());

    d->pipe_->invokeMethod(&PipelineHandler::queueRequest,
                   ConnectionTypeQueued, request);

    return 0;
}

/**
 * \fn PipelineHandler::queueRequest()
 * \brief Queue a request
 * \param[in] request The request to queue
 *
 * This function queues a capture request to the pipeline handler for
 * processing. The request is first added to the internal list of waiting
 * requests which have to be prepared to make sure they are ready for being
 * queued to the pipeline handler.
 *
 * The queue of waiting requests is iterated and up to \a
 * maxQueuedRequestsDevice_ prepared requests are passed to the pipeline handler
 * in the same order they have been queued by calling this function.
 *
 * If a Request fails during the preparation phase or if the pipeline handler
 * fails in queuing the request to the hardware the request is cancelled.
 *
 * Keeping track of queued requests ensures automatic completion of all requests
 * when the pipeline handler is stopped with stop(). Request completion shall be
 * signalled by the pipeline handler using the completeRequest() function.
 *
 * \context This function is called from the CameraManager thread.
 */
void PipelineHandler::queueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->waitingRequests_.push(request);

    request->_d()->prepare(300ms);
}

/**
 * \brief Queue one requests to the device
 */
void PipelineHandler::doQueueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_device_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->queuedRequests_.push_back(request);

    request->_d()->sequence_ = data->requestSequence_++;

    if (request->_d()->cancelled_) {
        completeRequest(request);
        return;
    }

    int ret = queueRequestDevice(camera, request);
    if (ret)
        cancelRequest(request);
}

/**
 * \brief Queue prepared requests to the device
 *
 * Iterate the list of waiting requests and queue them to the device one
 * by one if they have been prepared.
 */
void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();
    while (!data->waitingRequests_.empty()) {
        if (data->queuedRequests_.size() == maxQueuedRequestsDevice_)
            break;

        Request *request = data->waitingRequests_.front();
        if (!request->_d()->prepared_)
            break;

        /*
         * Pop the request first, in case doQueueRequests() is called
         * recursively from within doQueueRequest()
         */
        data->waitingRequests_.pop();
        doQueueRequest(request);
    }
}

\brief Stop capture from camera
 *
 * This function stops capturing and processing requests immediately. All
 * pending requests are cancelled and complete synchronously in an error state.
 *
 * \context This function may be called in any camera state as defined in \ref
 * camera_operation, and shall be synchronized by the caller with other
 * functions that affect the camera state. If called when the camera isn't
 * running, it is a no-op.
 *

 * \retval -ENODEV The camera has been disconnected from the system
 * \retval -EACCES The camera is not running so can't be stopped
 */

{
    Private *const d = _d();

    /*
     * \todo Make calling stop() when not in 'Running' part of the state
     * machine rather than take this shortcut
     */
    if (!d->isRunning())
        return 0;

    int ret = d->isAccessAllowed(Private::CameraRunning);
    if (ret < 0)
        return ret;

    LOG(Camera, Debug) << "Stopping capture";

    d->setState(Private::CameraStopping);

    d->pipe_->invokeMethod(&PipelineHandler::stop, ConnectionTypeBlocking,
                   this);

    ASSERT(!d->pipe_->hasPendingRequests(this));

    d->setState(Private::CameraConfigured);

    return 0;
}

\brief Stop capturing from all running streams and cancel pending requests
 * \param[in] camera The camera to stop
 *
 * This function stops capturing and processing requests immediately. All
 * pending requests are cancelled and complete immediately in an error state.
 *
 * \context This function is called from the CameraManager thread.
 */
void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());

    data->requestSequence_ = 0;
}
