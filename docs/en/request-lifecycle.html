Verification scope: Linking code evidence to explanations

Terms in this document: fence, Pipeline Handler, EEXIST, errno and 6 others
  • fence: A synchronization signal that indicates when a buffer may be used. If a valid fence is attached to a request, the request waits for this signal in the preparation stage. It is different from the request completion signal.
  • Pipeline Handler: A libcamera component that finds the media device of a specific hardware platform (IPU3, RKISP1, etc.), creates cameras, passes requests to the device, and returns their completion. There is one per platform.
  • EEXIST: Returns the -EEXIST error when a buffer still has an unreleased fence or a buffer is already registered on the same stream.
  • errno: The standard error number that Linux functions use to report the cause of a failure. libcamera functions return this value as a negative number. For example, -ENODEV means no device, -EACCES means access denied, -EINVAL means invalid argument, -ENOMEM means out of memory, and -EXDEV means a resource that belongs to another object.
  • Pending: The request state in which the request has not yet changed to completed or canceled. It does not mean device processing has started, and if a preceding request is in this state, the return of a following request may also have to wait.
  • ASSERT: libcamera's debug-check macro. In debug builds, if the condition is false, it logs a fatal message and aborts execution.
  • WSL2 (Windows Subsystem for Linux 2): An environment for running Linux on Windows. This site is built from the results of building and extracting libcamera on WSL2.
  • DMA (Direct Memory Access): DMA (Direct Memory Access) is a term for a method in which an I/O device reads from or writes to system memory directly.
  • ISP (Image Signal Processor): A processing unit that converts raw (Bayer) data output by the sensor into an image that can be displayed on screen. It performs operations such as black level correction, lens shading correction, white balance, and debayering.
  • HAL (Hardware Abstraction Layer): A layer that lets the operating system handle hardware that differs by manufacturer through the same interface. The final deployment target of this project is the in-house Android Camera HAL.

Other terms can be found in Glossary.

From submission to completion

A 0 return from queueRequest means that a queued call to the pipeline target was scheduled successfully; it does not mean the request has completed. completeRequest notifies the camera that a request has already completed. A pipeline handler may call it without any ordering constraint, and requests are returned to the application in submission order.

The return type of Camera::createRequest(uint64_t cookie) is std::unique_ptr<Request>. The object returned by this function is an empty Request object created so that the application can fill it with buffers and parameters and queue it for capture. If creation fails, it returns nullptr.

Request::addBuffer is an API that adds FrameBuffer to the request and connects the buffer to the stream to which the buffer belongs, as specified by the stream argument. Because a request can hold only one buffer per stream, -EEXIST is returned if the same stream already has a buffer or if the buffer still references a fence. -EINVAL is returned if the buffer does not reference a valid Stream.

If the request passes validation, Camera::queueRequest() calls PipelineHandler::queueRequest through invokeMethod using the ConnectionTypeQueued mode and then returns 0. Because ConnectionTypeQueued is an asynchronous mode in which the caller does not wait for the target to finish, a return value of 0 indicates success, and request completion is notified separately through the requestCompleted signal.

If prepared_ of the leading request in waitingRequests_ is false, doQueueRequests() stops the loop, so the requests behind it are also not passed to the device. In contrast, if queuedRequests_.size() equals maxQueuedRequestsDevice_, the loop stops; because this queuedRequests_ is a software queue that adds requests before they are passed to the device, its size cannot be read as the number of requests passed to the device, and cancelled requests may also be included in it.

doQueueRequest is a void function, so it does not return a value to the caller. The function adds the request to queuedRequests_, assigns sequence_, and then checks request->_d()->cancelled_. If cancelled_ is true, it calls completeRequest(request) and returns, so queueRequestDevice is not called. If cancelled_ is false, it calls queueRequestDevice(camera, request), and calls cancelRequest(request) only when the result ret is not 0.

The PipelineHandler::queueRequestDevice() function queues a capture request to the device. On success it returns 0, and when an error occurs it returns a negative error code. Pipeline handlers must call completeBuffer from the CameraManager thread when signaling buffer completion. Even when the last buffer completes, the request is not completed automatically, so the handler must explicitly call completeRequest separately.

completeRequest checks the front request in queuedRequests_, and if that request's status() is RequestPending, it stops the iteration. If it is not RequestPending, it confirms there are no pending buffers with ASSERT(!req->hasPendingBuffers()), then removes the request from the front of the queue and calls camera->requestComplete(req). According to the comment, this process returns requests to the application in submission order.

Lifetime of requests, buffers, and fences

The caller that created the request is responsible for deleting it. The caller that added a buffer to the request must ensure the buffer remains valid until the request completion callback is called. The pipeline handler must not access the request after completeRequest returns.

Ownership of the request returned by createRequest passes to the caller. The caller is responsible for deleting this request and may also delete it in the completion handler. The caller may also reuse this request after resetting its state with Request::reuse().

Request::addBuffer() stores a reference to the passed-in FrameBuffer in the request. The caller must ensure that the buffer remains valid until the request completion callback is invoked.

When a valid Fence is passed to addBuffer, addBuffer moves fence to buffer. Ownership of Fence is taken only when addBuffer succeeds, and in that case the object that receives ownership is buffer. If that call fails, fence remains unmodified.

If Request::addBuffer() fails, the fence that was passed in is not moved to buffer and remains as it is. According to the source comment, ownership of fence is taken only on success, and on failure fence is left unchanged. Also, if buffer still references fence, the same function returns -EEXIST.

If the fence is not signaled, the request fails after a timeout. In this case, the fence remains in the buffer as is. The application must retrieve the fence with FrameBuffer::releaseFence() before reusing the buffer in another request.

Request::ReuseBuffers is a flag that reuses buffers previously added by addBuffer(), keeping the existing buffers. Fences attached to buffers are not reused even when this flag is specified. When fences are used, the documentation recommends avoiding this flag.

The pipeline handler must call completeRequest to notify the camera that the request has completed. After this function returns, the request is no longer managed by the pipeline handler, and the pipeline handler must not access that request. cancelRequest cancels the request with request->_d()->cancel() and then calls completeRequest, and the source states that the same rules as for completeRequest apply to this function.

Distinguishing stop and disconnect

PipelineHandler::stop is a function that stops capture from all running streams, and according to its documentation, it cancels all waiting requests and completes them immediately in an error state. In contrast, Camera::disconnect contains only a TODO about handling waiting requests when a running camera is disconnected, and the source text does not state how they are handled.

/**

void PipelineHandler::doQueueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_device_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->queuedRequests_.push_back(request);

    request->_d()->sequence_ = data->requestSequence_++;

/**
 * \brief Queue prepared requests to the device
 *
 * Iterate the list of waiting requests and queue them to the device one
 * by one if they have been prepared.
 */
void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();
    while (!data->waitingRequests_.empty()) {
        if (data->queuedRequests_.size() == maxQueuedRequestsDevice_)
            break;

         * recursively from within doQueueRequest()
