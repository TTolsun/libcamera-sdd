Read code structure together with evidence, from the camera API through Pipeline Handler and IPA.

These design documents are generated for review from public libcamera source. They use navigation inspired by official libcamera documentation and OMM's reading-oriented design.

Reading order

If you are diagnosing an integration error, start with Request lifecycle and troubleshooting. If you are changing internals, start with the system overview and examine the evidence for the relevant pipeline and algorithm.

Task Read first What to establish
Reuse requests and buffers safely. Request lifecycle and troubleshooting Check each resource's lifetime and reuse conditions.
Find why completion is missing after successful submission. Request lifecycle and troubleshooting Distinguish submission failure, preparation waits, device processing and completion notification.
Change pipeline completion or stop code. Pipeline Handler Check in-order returns and the contract for handling waiting requests during stop.
Change IPU3 LSC controls or update conditions. IPU3 LSC configuration and frame processing Check parameter updates for each condition and the runtime validation still required.
  1. Start with System overview to understand camera discovery, request creation and completion responsibilities, and capture-session states. Then find the relevant packages.
  2. Use Core scenarios to inspect the main calls and static-trace boundaries for request submission, completion, capture stopping and cancellation.
  3. Read Request lifecycle and troubleshooting to connect submission, completion, reuse and stopping. Use Camera and request model for ownership and state transitions, Pipeline Handler for request queues, completion and stop contracts, and IPA management and implementation entry points for module selection, execution boundaries, inputs, outputs and errors.
  4. IPU3 LSC These two documents follow one algorithm from start to finish.

The Next step link at the end of each page follows this reading order.

The Responsibility column comes from documentation comments in the source. libcamera sometimes documents classes separately in implementation files, so both declaration comments and implementation-file documentation are read.

Each page includes extracted classes, structural explanations, relationship diagrams and code evidence. Click a diagram to enlarge it or search for a class. Source links point to the file and line at the exact commit used for analysis.

Design-contract documents link each question to its explanation. Expand the source excerpts below an explanation to compare them. Read runtime-check items separately from behavior established in the code.

Expand or collapse child documents in the left menu. Only the branch containing the current document starts expanded.

Scenario checkpoints and diagrams use call evidence selected in the configuration. The trace-boundary table identifies virtual-call candidates and dispatch targets. Diagrams do not establish execution order. Expand each range within the page to see all trace records, including logging and accessor calls.

Reading the review status

Generated documents without human approval are marked Human review pending. ok means the automatic checks for that generation method passed; it does not mean the explanation's accuracy was approved. needs-review means automatic checks still identify issues to examine.

See the document list below for current check results and approval status. Each page identifies its generation method and validation scope, such as explanations from extracted facts, design explanations bound to source excerpts, or LLM prose. Matching excerpt hashes and passing automatic checks do not replace human content review. Class diagrams also do not guarantee execution order or physical-device behavior.

The 4B and 9B models were compared using the same evidence. Both still had errors or omissions in ownership, shutdown and execution-boundary explanations. Comparison record preserves the original outputs and assessment evidence. Those experimental drafts were not adopted as this site's design explanations.

Analysis and publication scope

Each document shows its analyzed source commit. The inputs were built and extracted in WSL2 with IPU3, RKISP1, UVC and GStreamer enabled. Overview, camera, Pipeline, IPA and LSC explanations are generated by checking contracts in the example configuration against source excerpts. Core scenarios include the stop and cancellation path of Camera::stop(). Scenarios show calls and boundaries extracted with libclang; capture on physical devices and runtime validation remain future work.

camera-hal-sdd-generator maintains analysis, generation, validation and site presentation. libcamera-sdd maintains source history and publishes the completed documents. The public environment has no recurring schedule. Work in the generator repository includes checking and synchronizing official upstream, updating the documents and publishing them. When there are no new commits, existing categories are checked for missing coverage. Scheduling and time changes remain available in the shared runner for internal operation.

For library usage, see Official libcamera documentation.
