Terms in this document: Pipeline Handler, V4L2, HAL, RK3399, and one other
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • V4L2 (Video4Linux2): the Linux kernel API for cameras and video devices. libcamera controls sensors and ISP devices through it.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • RK3399 is a Rockchip system-on-chip (SoC). The official documentation lists it as a supported target of the rkisp1 pipeline handler.
  • IPU6 is a generation of the Intel Image Processing Unit (IPU). The official documentation lists it as a supported target of the simple pipeline instead of a dedicated handler.

Other terms are in the Glossary.

What it is and whose problem it solves

libcamera is an open-source complex camera support library for Linux, Android, and ChromeOS. It connects to Linux kernel device drivers and provides an API to developers, reducing the complexity of capturing images with complex cameras on Linux systems. libcamera provides a complete camera stack for Linux-based systems. The stack abstracts the hardware configuration and image control algorithms needed to obtain the desired results from a camera through the kernel API, allowing developers to handle this work in a simple and consistent way.

Providing a working camera stack using drivers is the responsibility of user space, and vendors often implement it separately without a common architecture or API for application developers. This work is made more complex because hardware pipelines and their representations in kernel APIs differ, often requiring custom handling. Kernel drivers at the bottom layer control camera hardware and provide low-level interfaces to user space. These interfaces use the Media Controller API, the V4L2 Video Device API, and the V4L2 Subdev API, which belong to the Linux kernel's V4L2 API family.

The libcamera framework above it controls camera devices through its core component, libcamera, and provides a native C++ API to higher layers. Optional language bindings allow other programming languages to connect to libcamera. The libcamera adaptation layer above it refers to components that connect other frameworks to libcamera. Examples include the V4L2 compatibility layer, the gstreamer libcamera element, and the Android camera HAL implementation based on libcamera.

Applications and higher-level frameworks at the top are built on the libcamera framework or libcamera adaptation. This layer is outside the scope of the libcamera project.

Supported hardware and build options

The documentation lists Arm Mali-C55, Intel IPU3 (ipu3), NXP i.MX8MP (imx8-isi and rkisp1), RaspberryPi 3, 4, and zero (rpi/vc4), and Rockchip RK3399 (rkisp1) as hardware platforms currently supported by dedicated pipeline handlers. The documentation states that the library provides generic support for USB video device class cameras (uvcvideo), iMX7, IPU6, and Allwinner Sun6i (simple), and a virtual media controller driver for testing (vimc).

Select the pipeline handlers to build using the array option pipelines. The available values are all, auto, imx8-isi, ipu3, mali-c55, rkisp1, rpi/pisp, rpi/vc4, simple, uvcvideo, vimc, and virtual. The default value, auto, builds all pipelines applicable to the target architecture, while all builds all pipelines. If both values are selected, all takes precedence.

Capabilities and support scope

Camera models a camera that can produce one or more image streams from a single image source. It provides the primary interface for device configuration and control and image stream capture, and is a central object provided by libcamera. A pipeline handler is responsible for matching the required media devices with devices in the system and creating the corresponding Camera instance if it can acquire all required devices. All PipelineHandler subclasses must be registered with libcamera using the REGISTER_PIPELINE_HANDLER() macro.

What device implementers gain from the common layer

PipelineHandler::queueRequest() first adds capture requests to the internal pending request list and prepares them for submission to the pipeline handler. This function iterates over the pending queue and submits up to maxQueuedRequestsDevice_ ready requests to the pipeline handler in the order they were registered with this function. If a request fails during preparation or the pipeline handler fails to register it in the hardware queue, the request is cancelled.

Tracking queued requests ensures all requests complete automatically when the pipeline handler is stopped with stop(). The pipeline handler must call completeBuffer() from the CameraManager thread to notify applications of the completion of buffers belonging to a request and to update the buffer tracking inside the request. Even when the last buffer completes, the request is not completed automatically, so the pipeline handler must explicitly call completeRequest().
