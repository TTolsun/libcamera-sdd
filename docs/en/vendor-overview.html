Terms in this document: Pipeline Handler, HAL
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.

What it is and whose problem it solves

libcamera is an open-source library for complex camera support on Linux, Android, and ChromeOS. This library works with Linux kernel device drivers and provides developers with an intuitive API, simplifying the complexity of capturing images with complex cameras on Linux systems. The responsibility for building a camera stack that operates using kernel drivers lies in user space, and this is generally implemented separately by each vendor without a common architecture or application developer API. In particular, because of differences in hardware pipelines and in how those differences are expressed in kernel APIs, custom handling is often necessary, which greatly increases the complexity of the work.

libcamera provides a complete camera stack for Linux-based systems. It abstracts the hardware configuration and image control algorithm settings required to obtain the desired results from a camera through kernel APIs, and reduces these operations to a simple, consistent method for developers. In the lowest layer of the camera stack, the kernel driver controls the camera hardware and exposes low-level interfaces to user space through the V4L2-family APIs of the Linux kernel, namely Media Controller API, V4L2 Video Device API, and V4L2 Subdev API.

Supported hardware and build options

libcamera is a hardware platform with dedicated pipeline handlers, and it supports Arm Mali-C55, Intel IPU3 (ipu3), NXP i.MX8MP (imx8-isi and rkisp1), RaspberryPi 3, 4, zero (rpi/vc4), and Rockchip RK3399 (rkisp1). Separately, libcamera provides general platform support for USB Video Class cameras (uvcvideo), iMX7, IPU6, Allwinner Sun6i (simple), and a virtual media controller driver for test use cases (vimc).

Capabilities and support scope

The Camera class models a camera that can produce one or more image streams from a single image source. This class provides the main interface for configuring and controlling the device and for capturing image streams, and it is the central object exposed by libcamera. Pipeline handlers are responsible for matching the required media devices to the devices present in the system, and must create the corresponding Camera instance once all required devices can be acquired. Each pipeline supported by libcamera must be backed by a pipeline handler implementation, and all subclasses of PipelineHandler must be registered with libcamera using the REGISTER_PIPELINE_HANDLER() macro.

What device implementers gain from the common layer

PipelineHandler::queueRequest() adds the received request to an internal wait list. This list is traversed, and up to maxQueuedRequestsDevice_ requests that are ready to be passed to the pipeline handler are passed to this function in the order in which they were called. If a request fails during preparation, or if the pipeline handler fails to queue the request to the hardware queue, that Request is canceled.

Device request limits and wait queues

In the constructor declaration of PipelineHandler, the default value of maxQueuedRequestsDevice is 32. The number of requests limited by maxQueuedRequestsDevice_ corresponds to the requests that the pipeline handler queues to the underlying hardware, that is, the device queue. The remaining requests stay in an internal wait queue and are queued at a later stage. The application can queue as many requests as it wants, but only maxQueuedRequestsDevice_ requests are queued to the hardware at a time, and the remaining requests wait in the internal wait queue until they are queued at a later stage.
