Terms in this document: Pipeline Handler, V4L2, HAL, IPU3, and 2 others.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • V4L2 (Video4Linux2): the Linux kernel API for cameras and video devices. libcamera controls sensors and ISP devices through it.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • IPU3 (Intel Image Processing Unit 3): the camera ISP in some Intel laptop processors. libcamera has a Pipeline Handler and an IPA for it.
  • RK3399 is a Rockchip system-on-chip (SoC). The official documentation lists it as a supported target of the rkisp1 pipeline handler.
  • IPU6 is a generation of the Intel Image Processing Unit (IPU). The official documentation lists it as a supported target of the simple pipeline instead of a dedicated handler.

Other terms are in the Glossary.

What it is and whose problem it solves

libcamera is an open source library for Linux, Android, and ChromeOS that supports complex cameras. The library simplifies the complexity of capturing images from complex cameras on Linux systems and interfaces with Linux kernel device drivers. It provides developers with an intuitive API.

libcamera provides a complete camera stack for Linux-based systems that abstracts, through the kernel's APIs, the configuration of hardware and the image control algorithms required to obtain desirable results from the camera, reducing those operations to a simple and consistent method for developers. With this abstraction, developers handle those operations through a simple and consistent method instead of dealing with them directly in this way. However, the excerpt ends at the introductory sentence ending with 'instead of having to deal with this:', so it is not confirmed from this evidence alone which specific operations are reduced.

The responsibility for implementing a working camera stack that uses the kernel drivers lies in userspace, and vendors commonly implement this separately, without a common architecture or API for application developers. Differences in hardware pipelines and in how they are represented in the kernel APIs often require bespoke handling.

Kernel drivers directly control the camera hardware. This layer exposes a low-level interface to userspace through the V4L2-family APIs of the Linux kernel. This API family includes the Media Controller API, the V4L2 Video Device API, and the V4L2 Subdev API.

The libcamera framework is the core part of the camera stack. Its core component, libcamera, handles all control of camera devices and exposes a native C++ API to upper layers. Optional language bindings allow libcamera to be interfaced from other programming languages. These components live in the same source code repository and together constitute the libcamera framework.

'Adaptation' is an umbrella term for components that interface libcamera with other frameworks. Notable examples include a V4L2 compatibility layer, a gstreamer libcamera element, and an Android camera HAL implementation based on libcamera. These components may live in separate repositories within the libcamera project source code, or may move to the repository of their respective projects, as the gstreamer libcamera element does.

The last layer consists of applications and upper-level frameworks. They are based on the libcamera framework or the libcamera adaptation. This layer is outside the scope of the libcamera project.

Supported hardware and build options

The document lists the following as hardware platforms it states are supported with dedicated pipeline handlers: Arm Mali-C55, Intel IPU3 (ipu3), NXP i.MX8MP (imx8-isi, rkisp1), RaspberryPi 3, 4 and zero (rpi/vc4), and Rockchip RK3399 (rkisp1). The document lists the following as generic platform support targets: USB video device class cameras (uvcvideo), iMX7, IPU6, Allwinner Sun6i (simple), and the virtual media controller driver for test use cases (vimc) are included in this category.

The build option pipelines is an array option that selects which pipeline handlers to build, and its default value is ['auto']. The listed choice values include all, auto, imx8-isi, ipu3, uvcvideo, virtual, and other individual handler names. Selecting auto builds all pipelines applicable to the target architecture, and selecting all builds all pipelines. If both values are selected together, all takes precedence.

Capabilities and support scope

The Camera class models a camera that can produce one or more image streams from a single image source. This class provides the main interface for configuring and controlling the camera device and for capturing image streams. A camera goes through the operations of acquisition, configuration, start, request processing, stop, and release, in that order. As long as it is not released, it may be started and stopped multiple times, and it may also be reconfigured. Functions that affect the camera state are generally not synchronized with each other by the Camera class, so the caller is responsible for ensuring their synchronization if necessary.

At request creation, when the prepared signal connected in registerRequest() is received, doQueueRequests(camera) is executed. doQueueRequests() repeats until waitingRequests_ is empty, and it stops repeating when the size of queuedRequests_ equals maxQueuedRequestsDevice_. If the prepared_ of the front request is false, it stops; if it is true, it passes the request to doQueueRequest() after pop(). Therefore, prepared requests are submitted in the order they entered the waiting list.

If Request fails during the preparation phase, or if the pipeline handler fails to queue the request to the hardware, the request is cancelled. This cancellation contract is documented in the comment in src/libcamera/pipeline_handler.cpp.

Because queued requests are tracked, all requests are guaranteed to complete automatically when the pipeline handler is stopped with stop(). The pipeline handler must call completeBuffer() from the CameraManager thread; this call notifies the application of buffer completion and updates the request's internal buffer tracking information. Because a request is not completed automatically when its last buffer completes, the pipeline handler must explicitly complete the request with completeRequest().

/**
 * \fn PipelineHandler::queueRequest()
 * \brief Queue a request
 * \param[in] request The request to queue
 *
 * This function queues a capture request to the pipeline handler for
 * processing. The request is first added to the internal list of waiting
 * requests which have to be prepared to make sure they are ready for being
 * queued to the pipeline handler.
 *
 * The queue of waiting requests is iterated and up to \a
 * maxQueuedRequestsDevice_ prepared requests are passed to the pipeline handler
 * in the same order they have been queued by calling this function.
 *
 * If a Request fails during the preparation phase or if the pipeline handler
 * fails in queuing the request to the hardware the request is cancelled.
 *
 * Keeping track of queued requests ensures automatic completion of all requests
 * when the pipeline handler is stopped with stop(). Request completion shall be
 * signalled by the pipeline handler using the completeRequest() function.
 *
 * \context This function is called from the CameraManager thread.
 */
void PipelineHandler::queueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->waitingRequests_.push(request);

    request->_d()->prepare(300ms);
}

/**
 * \brief Queue one requests to the device
 */
void PipelineHandler::doQueueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_device_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->queuedRequests_.push_back(request);

    request->_d()->sequence_ = data->requestSequence_++;

    if (request->_d()->cancelled_) {
        completeRequest(request);
        return;
    }

    int ret = queueRequestDevice(camera, request);
    if (ret)
        cancelRequest(request);
}

/**
 * \brief Queue prepared requests to the device
 *
 * Iterate the list of waiting requests and queue them to the device one
 * by one if they have been prepared.
 */
void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();
    while (!data->waitingRequests_.empty()) {
        if (data->queuedRequests_.size() == maxQueuedRequestsDevice_)
            break;

        Request *request = data->waitingRequests_.front();
        if (!request->_d()->prepared_)
            break;

        /*
         * Pop the request first, in case doQueueRequests() is called
         * recursively from within doQueueRequest()
         */
        data->waitingRequests_.pop();
        doQueueRequest(request);
    }
}
