Terms in this document: Pipeline Handler, HAL, IPU3, RK3399, and 1 other
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • HAL (Hardware Abstraction Layer): the layer that lets an operating system drive different vendors' hardware through one interface. This project ultimately targets an in-house Android Camera HAL.
  • IPU3 (Intel Image Processing Unit 3): the camera ISP in some Intel laptop processors. libcamera has a Pipeline Handler and an IPA for it.
  • RK3399: The name of a system-on-chip (SoC) made by Rockchip. This document lists it as a platform supported by the rkisp1 Pipeline Handler.
  • IPU6: The name of a generation of the Intel Image Processing Unit (IPU) family. This document lists it as a platform supported by the generic (simple) pipeline without a dedicated Pipeline Handler.

What it is and whose problem it solves

libcamera is an open-source library for supporting complex cameras on Linux, Android, and ChromeOS. It connects to Linux kernel device drivers and provides developers with an intuitive API, simplifying the complex task of capturing images with complex cameras on Linux systems. Providing a functioning camera stack using the drivers is the responsibility of user space, and vendors have typically implemented it independently, without a common architecture or API for application developers. This work is complex because hardware pipelines and the way they are represented in kernel APIs vary, often requiring custom handling.

libcamera provides a complete camera stack for Linux-based systems. It abstracts the hardware configuration and image control algorithms needed to obtain the desired results from cameras through the kernel's APIs, allowing developers to handle this work in a simple and consistent way. Kernel drivers, the lowest layer of the camera stack, control camera hardware and provide low-level interfaces to user space through the Linux kernel's V4L2 family of APIs. These APIs include Media Controller API, V4L2 Video Device API, and V4L2 Subdev API.

Supported hardware and build options

The documentation lists Arm Mali-C55, Intel IPU3 (ipu3), NXP i.MX8MP (imx8-isi and rkisp1), RaspberryPi 3, 4 and zero (rpi/vc4), and Rockchip RK3399 (rkisp1) as hardware platforms supported by dedicated pipeline handlers. The generic support targets specified in the documentation are USB video device class cameras (uvcvideo), iMX7, IPU6 and Allwinner Sun6i (simple), and a virtual media controller driver for testing (vimc).

Select the pipeline handlers to build using the array option pipelines. The default is auto, which builds all pipelines applicable to the target architecture. Selecting all builds all pipelines, and if both auto and all are selected, all takes precedence. The individual selection values are imx8-isi, ipu3, mali-c55, rkisp1, rpi/pisp, rpi/vc4, simple, uvcvideo, vimc, and virtual.

Capabilities and support scope

Camera models a camera that can produce one or more image streams from a single image source. It is the central object in libcamera, providing the main interface for configuring and controlling the device and capturing image streams. Once a pipeline handler has matched the required media devices against the devices in the system and can acquire all required devices, it must create the corresponding Camera instances. All PipelineHandler subclasses must be registered with libcamera using the REGISTER_PIPELINE_HANDLER() macro.

What device implementers gain from the common layer

The common PipelineHandler::queueRequest first adds the capture request to an internal pending request list for processing. The request then goes through a preparation process to determine whether it is ready to be queued to the pipeline handler. This function traverses the pending request queue and passes up to maxQueuedRequestsDevice_ ready requests to the pipeline handler in the order they were queued to this function. If a request fails during preparation or the pipeline handler fails to queue it to the hardware, the request is cancelled.

Paragraph evidence · 2
  • src/libcamera/pipeline_handler.cppL447 excerpt · Full source L447 · L460 excerpt · Full source L460

Tracking queued requests ensures that all requests are automatically completed when the pipeline handler is stopped with stop(), and the pipeline handler must signal request completion with completeRequest(). In contrast, a request is not automatically completed when its last buffer completes in completeBuffer(), so the pipeline handler must explicitly call completeRequest().

Device request limits and wait queues

In the PipelineHandler constructor declaration, the default value of maxQueuedRequestsDevice is 32. maxQueuedRequestsDevice_ limits the number of requests that the pipeline handler must keep queued to the underlying hardware at a time, while the remaining requests wait in an internal pending queue. If the application submits more requests than the device limit, the remaining requests wait in the internal pending queue until they are queued to the hardware later.
