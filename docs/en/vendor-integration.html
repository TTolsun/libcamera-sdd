Review the integration sequence and implementation responsibilities, then apply the configuration, request, and shutdown contracts.

Terms in this document: Pipeline Handler, IPA, proxy
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.
  • Proxy: a stand-in object that takes calls through the same interface instead of calling the IPA module directly, and forwards them to the IPA thread or a separate process. It is generated from the mojom definition at build time.

Other terms are in the Glossary.

Integration sequence and responsibilities

The application must acquire and configure a camera before processing requests, then start it. A started camera can process requests until it is stopped, and when the application finishes using the camera, the camera must be released. The application may start and stop a camera several times without releasing it, and the camera may be reconfigured. Functions that affect the state of Camera are generally not synchronized with each other by the Camera class. When synchronization is needed, the caller must guarantee that synchronization.

Boundary between hardware and the common layer

When an implementer of PipelineHandler::match(DeviceEnumerator *enumerator) finds all media devices required for a single pipeline, it must acquire all those devices with MediaDevice::acquire() calls, then create one or more Camera instances, store them internally, return true, and register the created Camera instances with CameraManager. An implementer of PipelineHandler::match() must acquire all required media devices with MediaDevice::acquire() and create a Camera instance, store it internally, and return true only when all required media devices have been found. Otherwise, it must not acquire any media devices, and if it has already acquired some, it must call MediaDevice::release() to release all acquired devices and then return false.

Configuration interfaces to implement

The caller of PipelineHandler::generateConfiguration() must populate roles with the list of use cases it intends to use. By examining the returned configuration, the caller can determine the selected streams and the default parameters of each stream. generateConfiguration generates the camera's default configuration for the list of stream roles specified by the caller; by examining the returned configuration, the caller can determine the selected streams and the default parameters of each stream. If generateConfiguration can satisfy the requested roles, it must return a valid CameraConfiguration; if it cannot, it must return a null pointer (nullptr).

Passing requests to the device and returning them

queueRequestDevice() queues a capture request to the device, and the pipeline handler must program the device so that the parameters included in the request are applied to the frames held in the request's buffers. According to the source comment, PipelineHandler::queueRequestDevice() is called on the CameraManager thread, and the implementation must return 0 on success and a negative error code on failure. When the buffer portion of a request completes, the pipeline handler must call completeBuffer to notify the application of buffer completion, and it must update the request's internal buffer tracking information. Even if the last buffer completes in completeBuffer, the request is not completed automatically; this is so that the pipeline handler has an opportunity to perform the work it still requires.

IPA module selection and failure conditions

In createIPA, the module(name, minVersion, maxVersion) call expression passes name as the first argument, minVersion as the second argument, and maxVersion as the third argument, in that order. IPAManager::module iterates over modules_, and when module->match(name, minVersion, maxVersion) first becomes true, it handles the module.get() pointer of that module with 반환 and ends the function with return, so it does not continue iterating. createIPA returns nullptr if m, the result of the module(name, minVersion, maxVersion) call, is absent (!m).

Responsibilities for stopping and handling errors

In PipelineHandler::stop(Camera *camera), waitingRequests.swap(data->waitingRequests_) runs first, and then stopDevice(camera) runs. PipelineHandler::stop(Camera *camera) moves pending requests aside before stopDevice() is called. Doing so ensures that even if completeRequest() is called inside stopDevice(), those requests are not re-queued. A device implementer of PipelineHandler::stopDevice() must immediately stop capture and request processing for all running streams of the camera specified by the camera argument, and must cancel all pending requests and immediately complete them with an error status.

After calling stopDevice(), PipelineHandler::stop() marks each pending request that was moved aside earlier from waitingRequests_ as canceled with request->_d()->cancel() and passes it to doQueueRequest(). According to the source comment, at this time doQueueRequest() assigns a sequence number to the request and temporarily places it in queuedRequests_ so that it is completed in completeRequest(). PipelineHandler::stop() uses the last two ASSERT to check whether both queuedRequests_ and waitingRequests_ are empty, and after the check finishes, it stores 0 in requestSequence_.

Contracts to check after implementation and execution limits

After PipelineHandler::completeRequest is called, the pipeline implementer no longer manages that request, and the request must not be accessed after the function returns. The pipeline handler may pass completed requests to completeRequest without ordering constraints, and completeRequest guarantees that these requests are returned to the application in submission order. The caller of completeRequest must call completeRequest on the CameraManager thread.

IPAModule *IPAManager::module(const char *name, uint32_t minVersion,
                  uint32_t maxVersion)

        if (module->match(name, minVersion, maxVersion))
            return module.get();

void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());
