Review the integration sequence and implementation responsibilities, then apply the configuration, request, and shutdown contracts.

Terms in this document: Pipeline Handler, IPA, proxy
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.
  • Proxy: a stand-in object that takes calls through the same interface instead of calling the IPA module directly, and forwards them to the IPA thread or a separate process. It is generated from the mojom definition at build time.

Other terms are in the Glossary.

Integration sequence and responsibilities

To prepare for capture, the application must acquire, configure, and then start the camera. Once started, the camera can process requests until it is stopped, and the application must release it when it has finished using it. The application can start and stop the camera multiple times while it remains acquired, and can also reconfigure it. Because the Camera class generally does not synchronize functions that affect the camera state with one another, the caller must synchronize these functions when necessary.

Boundary between hardware and the common layer

When the PipelineHandler::match() implementer finds all media devices required for a single pipeline, it must call MediaDevice::acquire() to acquire all the devices, then create and store one or more corresponding Camera instances, register them with the camera manager, and return true. If the PipelineHandler::match() implementer cannot find all required media devices and has not yet acquired any devices, it must not acquire any media devices; if it has already acquired some, it must release all acquired devices using MediaDevice::release() and return false. PipelineHandler::match() is called from the CameraManager thread, and if it returns true, a new PipelineHandler instance is created and its match() is called.

Configuration interfaces to implement

The caller of generateConfiguration must populate roles with the use cases for which it wants to obtain a default configuration. The configuration returned by generateConfiguration() contains the selected streams and information about the default parameters for each stream. PipelineHandler::generateConfiguration() must return a valid CameraConfiguration if it can satisfy the requested roles, and otherwise must return a null pointer. Because PipelineHandler::generateConfiguration() may be called from any thread, the implementation must be thread-safe.

Implementers of PipelineHandler::generateConfiguration() must not change the state of camera within the pipeline handler. The configuration passed to PipelineHandler::configure() is guaranteed to have been validated by CameraConfiguration::validate(), so the pipeline handler implementation must not perform additional validation. The implementation of PipelineHandler::configure() may rely on all custom fields stored in its own CameraConfiguration derived class. When configuring the camera, implementers of PipelineHandler::configure() must use StreamConfiguration::setStream() to associate a Stream instance with each StreamConfiguration entry in CameraConfiguration.

PipelineHandler::configure() is called on the CameraManager thread, and the implementation must return 0 on success and a negative error code on failure.

Passing requests to the device and returning them

When processing a request containing a set of buffers associated with streams and a set of parameters, the queueRequestDevice implementer must configure the device so that the parameters are applied to the frames captured into the buffers provided in the request. The queueRequestDevice implementer must return 0 on success or a negative error code on failure. PipelineHandler::queueRequestDevice() is called on the CameraManager thread.

The pipeline handler must call completeBuffer() from the CameraManager thread to signal completion of a request's buffer. This function notifies the application that the buffer has completed and updates the buffer tracking information inside the request. The request is not completed automatically even when the last buffer completes, so the pipeline handler must explicitly call completeRequest() to complete the request.

IPA module selection and failure conditions

When calling module, createIPA passes name, representing the name, minVersion, representing the minimum version, and maxVersion, representing the maximum version, in that order. IPAManager::module iterates through the modules and, upon the first match for the name and allowed version range, returns that module and ends the search. If no matching module is found by the end, it returns nullptr. createIPA receives the result of module in m and returns nullptr if !m.

The lambda inside createIPA creates a T::Threaded object if isSignatureValid(m) is true, and a T::Isolated object if it is false. If the created proxy fails the isValid check, createIPA logs the error message Failed to load proxy and returns nullptr. If the created proxy passes validation, createIPA returns that proxy.

Responsibilities for stopping and handling errors

PipelineHandler::stop() first calls waitingRequests.swap(data->waitingRequests_) and then calls stopDevice(camera). PipelineHandler::stop() moves all waiting requests aside so that waiting requests are not requeued when completeRequest() is called inside stopDevice(). The implementer of stopDevice() must immediately stop capturing and request processing for all running streams, cancel all incomplete requests for that device, and complete them immediately in an error state.

After calling stopDevice(), PipelineHandler::stop() cancels the waiting requests one by one and passes them to doQueueRequest(). Along this path, it assigns a sequence number to each request and temporarily adds it to queuedRequests_ so that it can be completed in completeRequest(). After processing the waiting requests, PipelineHandler::stop() uses two ASSERT to check whether queuedRequests_ and waitingRequests_ are empty, and stores 0 in requestSequence_.

Contracts to check after implementation and execution limits

After completeRequest returns, the pipeline handler must not access that request, which it no longer manages. The pipeline handler may pass a completed request to completeRequest without any ordering constraint, and this function returns requests to the application in submission order. The pipeline handler must call completeRequest on the CameraManager thread.

\brief Release exclusive access to the camera device
 *
 * Releasing the camera device allows other users to acquire exclusive access
 * with the acquire() function.
 *
 * \context This function may only be called when the camera is in the
 * Available or Configured state as defined in \ref camera_operation, and shall
 * be synchronized by the caller with other functions that affect the camera
 * state.
 *
 * \return 0 on success or a negative error code otherwise
 * \retval -EBUSY The camera is running and can't be released
 */
int Camera::release()
{
    Private *const d = _d();

    int ret = d->isAccessAllowed(Private::CameraAvailable,
                     Private::CameraConfigured, true);
    if (ret < 0)
        return ret == -EACCES ? -EBUSY : ret;

    if (d->isAcquired())
        d->pipe_->invokeMethod(&PipelineHandler::release,
                       ConnectionTypeBlocking, this);

    d->setState(Private::CameraAvailable);

    return 0;
}

void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());

    data->requestSequence_ = 0;
}
