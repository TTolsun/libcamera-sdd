Review the integration sequence and implementation responsibilities, then apply the configuration, request, and shutdown contracts.

Terms on this page: Pipeline Handler, IPA, proxy, ASSERT
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.
  • Proxy: a stand-in object that takes calls through the same interface instead of calling the IPA module directly, and forwards them to the IPA thread or a separate process. It is generated from the mojom definition at build time.
  • ASSERT: libcamera's debug check macro. In debug builds, a false condition logs a fatal message and aborts execution.

Other terms are in the Glossary.

Integration sequence and responsibilities

The application must acquire and configure Camera, start it to process requests, then stop and release it when finished. State-changing functions are generally not synchronized with each other, so the caller must provide any required synchronization.

Boundary between hardware and the common layer

If match() finds all required media devices, the implementation must acquire them using MediaDevice::acquire(), create the corresponding Camera instances, store them internally and register them with the camera manager. It must return true in this case.

generateConfiguration() is required to return a valid configuration if the caller-specified stream roles can be satisfied, or a null pointer otherwise. The implementation must be safe to call from any thread and must not modify the camera state in the pipeline handler.

Passing requests to the device and returning them

The queueRequestDevice() implementation must program the device so that the request parameters apply to the frames captured in the request buffers. This function is called from the CameraManager thread and must return 0 on success or a negative error code on failure.

Responsibilities for stopping and handling errors

The common stop() implementation moves waitingRequests_ into a separate queue before calling stopDevice(). This prevents waiting requests from being requeued when completeRequest() is called inside stopDevice(). Waiting requests are cancelled after stopping the device to preserve request order.

Paragraph evidence · 1
  • src/libcamera/pipeline_handler.cppL359 excerpt · Full source L359

Under the stopDevice() contract, the device implementation must stop capture and request processing immediately, cancel all pending requests and complete them immediately in an error state. This excerpt describes an implementation obligation, not a test result from a specific device.

Paragraph evidence · 1
  • src/libcamera/pipeline_handler.cppL359 excerpt · Full source L359

After stopDevice(), stop() marks waiting requests as cancelled using cancel() and passes them to doQueueRequest(). This path assigns a sequence number and temporarily adds them to queuedRequests_ so that completeRequest() can complete them properly. Finally, ASSERT checks that both request queues are empty and requestSequence_ is reset to 0.

Contracts to check after implementation and execution limits

The pipeline handler must not access a request after completeRequest() returns. The request may be deleted immediately after return, so this access restriction must be respected.

template<typename T>
    std::unique_ptr<T> createIPA(const char *name, uint32_t minVersion,
                     uint32_t maxVersion)
    {
        IPAModule *m = module(name, minVersion, maxVersion);
        if (!m)
            return nullptr;

        auto proxy = [&]() -> std::unique_ptr<T> {
            if (isSignatureValid(m))
                return std::make_unique<typename T::Threaded>(m, cm_);
            else
                return std::make_unique<typename T::Isolated>(m, cm_);
        }();

        if (!proxy->isValid()) {
            LOG(IPAManager, Error) << "Failed to load proxy";
            return nullptr;
        }

        return proxy;
    }

\brief Stop capturing from all running streams and cancel pending requests
 * \param[in] camera The camera to stop
 *
 * This function stops capturing and processing requests immediately. All
 * pending requests are cancelled and complete immediately in an error state.
 *
 * \context This function is called from the CameraManager thread.
 */
void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());

    data->requestSequence_ = 0;
}
