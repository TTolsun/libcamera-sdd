Terms in this document: errno, Pending, Pipeline Handler
  • errno: the standard error numbers Linux functions use to report why they failed. libcamera functions return them as negative values. For example, -ENODEV means no device, -EACCES access denied, -EINVAL an invalid argument, -ENOMEM out of memory and -EXDEV a resource that belongs to another object.
  • Pending: A request state that has not yet changed to complete or cancelled. It does not mean device processing has started; an earlier request in this state can delay later returns.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.

Other terms are in the Glossary.

Narrowing down configuration failure

During the investigation, we will observe the return value ret of the existing isAccessAllowed call inside Camera::configure, which passes Private::CameraAcquired and Private::CameraConfigured as arguments. If ret < 0, we will record the failure branch in which Camera::configure returns the same ret. First, we will distinguish the preceding branch in the investigation: when allowDisconnected is false and disconnected_ is true, the existing Camera::Private::isAccessAllowed call returns -ENODEV. Otherwise, we will examine the range comparison of currentState with low and high and the return of 0 when it is within range; when it is outside the range, we will check the code locations of ASSERT, the error log, and the return of -EACCES, in that order.

After the access check passes, Camera::queueRequest() returns -EXDEV if the camera that created the request differs from the current camera. Next, Camera::queueRequest() returns -EINVAL if the request status is not RequestPending. It then compares controls().infoMap() with the address of the camera's controls() to check that the controls list has not been overwritten with another list; if they do not match, Camera::queueRequest() returns -EINVAL.

If the buffer map is empty, queueRequest returns -EINVAL at that check. It then checks each buffer's stream and returns -EINVAL if any stream is not in activeStreams_. If all preceding checks pass, queueRequest preprocesses AeEnable with patchControlList, then schedules PipelineHandler::queueRequest with ConnectionTypeQueued and returns 0.

The comment explains that -ENOMEM is returned when no buffer memory is available to handle the request. The implementation has no branch that directly returns -ENOMEM.

During the investigation, observe the result of the fence check buffer->_d()->fence() and the return value in the existing Request::addBuffer() call. If a fence is present, the function returns -EEXIST and does not reach try_emplace. If the fence check passes, observe inserted after try_emplace; if this value is false, a buffer already exists for the same stream, and the function returns -EEXIST. The return value -EEXIST alone does not establish which of the two causes applies.

When investigating after a successful submission, you can record and compare the values of queuedRequests_.size() and maxQueuedRequestsDevice_ in doQueueRequests() while there are waiting requests. If the two values are equal, you can observe the branch that exits the loop; if they are not equal, you can observe the next branch, which checks the prepared_ value of the first waiting request. In doQueueRequests, when there is a waiting request and the number of queued requests does not equal maxQueuedRequestsDevice_, observe and record both the first waiting request's prepared_ value and the branch that exits the loop with break if that value is false.

The investigation of doQueueRequest will check the path that calls completeRequest and then returns if cancelled_ is true. If false, it will observe the return value ret from the existing queueRequestDevice call and check the branch that calls cancelRequest when ret is nonzero.

During the investigation, observe the bufferCompleted notification, which passes request and buffer, and the return value in the existing completeBuffer call. The function updates the request's internal buffer completion state after sending the notification. If all buffers in the request have completed, the function returns true; otherwise, the function returns false. Even when the last buffer completes, the request is not completed automatically, so the pipeline handler must call completeRequest separately.

The investigation of completeRequest() will observe whether the request at the front of the queue has status Request::RequestPending. If it has that status, the investigation will examine the branch that exits the loop with break, leaving the front request in the queue and, in accordance with submission order, also preventing already completed requests behind it from being returned via requestComplete(). If the front request does not have that status, the investigation will observe the sequence in which ASSERT(!req->hasPendingBuffers()); checks the negated condition that there are no pending buffers, then pop_front() removes the front request and requestComplete(req) is called.

 * \param[in] config The camera configurations to setup
 *
 * Prior to starting capture, the camera must be configured to select a
 * group of streams to be involved in the capture and their configuration.
 * The caller specifies which streams are to be involved and their configuration
 * by populating \a config.
 *
 * The configuration is created by generateConfiguration(), and adjusted by the
 * caller with CameraConfiguration::validate(). This function only accepts fully
 * valid configurations and returns an error if \a config is not valid.

                     ConnectionTypeBlocking, this, config);

\brief Queue a request to the camera
 * \param[in] request The request to queue to the camera
 *
 * This function queues a \a request to the camera for capture.
 *
 * After allocating the request with createRequest(), the application shall
 * fill it with at least one capture buffer before queuing it. Requests that
 * contain no buffers are invalid and are rejected without being queued.
 *
 * Once the request has been queued, the camera will notify its completion
 * through the \ref requestCompleted signal.
 *
 * \context This function is \threadsafe. It may only be called when the camera
 * is in the Running state as defined in \ref camera_operation.
 *
 * \return 0 on success or a negative error code otherwise
 * \retval -ENODEV The camera has been disconnected from the system
 * \retval -EACCES The camera is not running so requests can't be queued
 * \retval -EXDEV The request does not belong to this camera
 * \retval -EINVAL The request is invalid
 * \retval -ENOMEM No buffer memory was available to handle the request
 */
int Camera::queueRequest(Request *request)
{
    Private *const d = _d();

    int ret = d->isAccessAllowed(Private::CameraRunning);
    if (ret < 0)
        return ret;

    /* Requests can only be queued to the camera that created them. */
    if (request->_d()->camera() != this) {
        LOG(Camera, Error) << "Request was not created by this camera";
        return -EXDEV;
    }

    if (request->status() != Request::RequestPending) {
        LOG(Camera, Error) << request->toString() << " is not valid";
        return -EINVAL;
    }

    /* Make sure the Request has a valid control list. */
    if (request->controls().infoMap() != &controls()) {
        LOG(Camera, Error) << "Overwriting Request::controls() is not allowed";
        return -EINVAL;
    }

    /*
     * The camera state may change until the end of the function. No locking
     * is however needed as PipelineHandler::queueRequest() will handle
     * this.
     */

    if (request->buffers().empty()) {
        LOG(Camera, Error) << "Request contains no buffers";
        return -EINVAL;
    }

    for (const auto &[stream, buffer] : request->buffers()) {
        if (d->activeStreams_.find(stream) == d->activeStreams_.end()) {
            LOG(Camera, Error) << "Invalid request";
            return -EINVAL;
        }
    }

    /* Pre-process AeEnable. */
    patchControlList(request->controls());

    d->pipe_->invokeMethod(&PipelineHandler::queueRequest,
                   ConnectionTypeQueued, request);

    return 0;
}

/**
 * \brief Queue one requests to the device
 */
void PipelineHandler::doQueueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_device_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->queuedRequests_.push_back(request);

    request->_d()->sequence_ = data->requestSequence_++;

    if (request->_d()->cancelled_) {
        completeRequest(request);
        return;
    }

    int ret = queueRequestDevice(camera, request);
    if (ret)
        cancelRequest(request);
}

/**
 * \brief Queue prepared requests to the device
 *
 * Iterate the list of waiting requests and queue them to the device one
 * by one if they have been prepared.
 */
void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();
    while (!data->waitingRequests_.empty()) {
        if (data->queuedRequests_.size() == maxQueuedRequestsDevice_)
            break;

        Request *request = data->waitingRequests_.front();
        if (!request->_d()->prepared_)
            break;

        /*
         * Pop the request first, in case doQueueRequests() is called
         * recursively from within doQueueRequest()
         */
        data->waitingRequests_.pop();
        doQueueRequest(request);
    }
}
