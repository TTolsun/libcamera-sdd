Distinguish successful request submission from completion in the public libcamera case, and decide on the next investigation task or whether to begin limited validation.

Terms in this document: ROI, HAL, Pipeline Handler, fence
  • ROI (Return on Investment): ROI is a concept that compares returns with investment costs, and it is not measured in this example from the public libcamera documentation.
  • HAL (Hardware Abstraction Layer): A layer that lets the operating system handle hardware that differs by manufacturer through the same interface. The final deployment target of this project is the in-house Android Camera HAL.
  • Pipeline Handler: A libcamera component that finds the media device of a specific hardware platform (IPU3, RKISP1, etc.), creates cameras, passes requests to the device, and returns their completion. There is one per platform.
  • fence: A synchronization signal that indicates when a buffer may be used. If a valid fence is attached to a request, the request waits for this signal in the preparation stage. It is different from the request completion signal.

Other terms can be found in Glossary.

Verification limits: The facts about this path are static source descriptions pinned to the analyzed commit. They are not results of reproducing missed completions on a device or measuring development time, quality, or ROI. Application to an in-house HAL and actual executive evaluation remain unverified.

Detailed explanations and source evidence are maintained in the linked reference document. The facts below reproduce the answers in that document verbatim. This path does not define organizational roles or approval authority.

Distinguishing successful submission from completion

Observed facts · Description of static sources

Applicability and limitations: This describes the common request path in the analyzed commit. It does not guarantee successful capture, completion times, or error recovery for a particular device.

When a request is scheduled for asynchronous delivery to the pipeline, queueRequest returns 0, which does not mean the request has completed. The pipeline handler must notify the camera of an already completed request using completeRequest, and completed requests are returned to the application in submission order.

Plan for investigating missing completions and verifying after a fix

Decision request · Not an approval

Decide whether to investigate the missing completion on the actual target. If proceeding, first establish an instrumentation plan that distinguishes among submission return values, request state, preparation or readiness waiting, the device queue, and completion callbacks. Do not determine the cause from the current documentation alone or change the state by calling observation functions again.

Category What to check
Required inputs The source, build, device, input configuration, reproduction sequence, submission return value, request status, and callback records are required.
The owner of the implementation to be modified, the effects on callers, threads, and resource lifetimes, and the conditions to check after success, failure, and stopping must be determined from the actual code.
Background evidence for the decision (not a measure of impact) Request submission error codes and check order · Check order by failure location
Options Once the required inputs are available, we will limit the scope, reproduce and measure the issue, and separately check submission and completion under the same conditions before and after the fix.
If the inputs or a reviewer are unavailable, we will defer starting and obtain the missing materials.

Applicability and limitations: This is an investigation plan, not an actual reproduction result. The investigation locations, observed values, and next branches are checked in the common diagnostic document.

Inputs needed for application and evaluation

  • Document-only responses, navigation paths, misunderstandings, and subjective relevance assessments are required from at least one actual non-author team member and at least one actual non-author technical decision-maker.

Human non-author evaluation, internal HAL verification, and evaluation by actual executives require separate verification.
