Terms in this document: IPA, Pipeline Handler
  • IPA (Image Processing Algorithms): a separate module (.so) holding the image-quality algorithms. It reads the statistics sent by the ISP and computes the ISP settings for the next frame. It is kept apart from libcamera itself so that vendors can ship it without publishing the source.
  • Pipeline Handler: the libcamera component that finds a hardware platform's media devices (IPU3, RKISP1 and so on), creates cameras, queues requests to the devices and returns completions. There is one per platform.

Other terms are in the Glossary.

Discovery and pipeline selection

CameraManager is the entry point of libcamera, enumerating devices and providing applications with access to the system's cameras. According to the introductory comment, CameraManager owns all Camera objects and manages camera lifetimes by handling hot-plugging and hot-unplugging. CameraManager::Private::pipelineFactoryMatch repeatedly creates PipelineHandler with the given factory and provides as many matching pipelines as possible while match(enumerator_.get()) returns true for each object. When match returns false, the iteration stops, and a Debug log is written only when matching succeeds.

Only one CameraManager instance may exist at the same time.

Execution check item: creating a second CameraManager instance without deleting the existing instance results in undefined behaviour. Therefore, the calling side must delete the existing instance before creating a new instance.

If CameraManager::start() succeeds, the application can list and use the cameras in the system enumerated during startup, and this state continues until the camera manager is stopped or the camera is unplugged from the system. CameraManager::cameras() and CameraManager::get() must be called while the camera manager is running, and the responsibility for ensuring this state rests with the caller.

Whoever implements match() must acquire all the required media devices by MediaDevice::acquire() once it finds all of the devices it needs. It must then create one or more Camera instances, store them internally, register them with the camera manager, and return true. If it fails to find all the required devices, it must either acquire no devices or release all the devices it has already acquired by MediaDevice::release(), and in both cases return false.

Component responsibilities

The Camera class represents a camera that can create one or more image streams from a single image source. It provides the main interface for configuring and controlling the device and capturing image streams, and it is the central object that libcamera exposes externally.

libcamera manages the lifetime of Camera instances with std::shared_ptr<>. Instances shall be created with the create() function, which returns a shared pointer. The constructors and destructor of Camera are declared private, so instances cannot be created or destroyed directly.

Request creation and ownership

The cookie of Camera::createRequest is an opaque input value for the application. This value is stored in the generated request and can be read again at any time with Request::cookie(). According to the source description, applications typically use this value in the completion handler to associate the request with an external resource, and from libcamera's perspective, cookie is a completely opaque value. Camera::createRequest() can only be called when the camera is in the Configured or Running state, and if an error occurs, the call returns nullptr.

The ownership of the request returned by Camera::createRequest() passes to the caller, and the responsibility for deleting that request also rests with the caller. To queue the same request again instead of creating a new one, the caller must call Request::reuse() before queuing that request to reset its state and associated controls. If flags & ReuseBuffers is true, Request::reuse(ReuseFlag) calls setRequest(this) on each buffer in bufferMap_ and inserts the buffer into _d()->pending_, keeping the buffers already added with addBuffer() and reusing them. If ReuseBuffers is not specified, bufferMap_ is emptied.

Capture-session states and resources

To prepare for capture, the application must acquire the camera with acquire(), configure it with configure(), and then start it with start(), in that order. A started camera can process requests until it is stopped, and this period is the Running state. The full shutdown path goes from Running to stop() through Stopping, returns to Configured after stopping, and then, from Configured, is released to Available with release(). As long as the camera is not released, the application may start and stop it multiple times, and it may also reconfigure the camera to change capture settings.

Request submission and completion

Before queuing it with Camera::queueRequest(), the application shall attach at least one capture buffer to the request object returned by createRequest(). When the request submitted with Camera::queueRequest() finishes processing, the camera notifies completion through the requestCompleted signal. Camera::queueRequest() may only be called when the camera is in the Running state defined in camera_operation.

Successful submission and capture completion are separate events

A zero return from queueRequest() reports successful submission. Completion is reported separately by requestCompleted.

Buffer completion and request completion

The pipeline handler must call PipelineHandler::completeBuffer() to signal that one buffer of the request has completed. completeBuffer() notifies the application of the buffer completion and updates the request's internal buffer tracking state. If all buffers included in the request have completed, completeBuffer() returns true; otherwise, completeBuffer() returns false. Even after the last buffer completes, the pipeline handler must explicitly call completeRequest().

Thread boundaries and synchronization

The functions that change the Camera state are not generally synchronized with each other by the Camera class, so the caller must ensure synchronization between these functions when necessary. The caller of PipelineHandler::completeRequest() is the pipeline handler. The pipeline handler must call this function when notifying the camera of a completed request, and that call must be made on the CameraManager thread.

Scope of static evidence

Camera::start() checks the camera state with d->isAccessAllowed(Private::CameraConfigured) and stores its return value in ret. If ret is negative (ret < 0), start() returns that value as is with return ret;, and in this branch the pipeline start call and the transition to the Private::CameraRunning state are not executed. The -EACCES in the API comment means a state in which the camera cannot start, but this code fragment alone cannot confirm whether isAccessAllowed() returns -EACCES, so the two values are not assumed to be the same. The subject this TODO comment asks to document is the camera start timing.

void CameraManager::Private::pipelineFactoryMatch(const PipelineHandlerFactoryBase *factory)
{
    CameraManager *const o = LIBCAMERA_O_PTR();

    /* Provide as many matching pipelines as possible. */
    while (1) {
        std::shared_ptr<PipelineHandler> pipe = factory->create(o);
        if (!pipe->match(enumerator_.get()))
            break;

        LOG(Camera, Debug)
            << "Pipeline handler \"" << factory->name()
            << "\" matched";
    }
}

\brief Reset the request for reuse
 * \param[in] flags Indicate whether or not to reuse the buffers
 *
 * Reset the status and controls associated with the request, to allow it to
 * be reused and requeued without destruction. This function shall be called
 * prior to queueing the request to the camera, in lieu of constructing a new
 * request. The application can reuse the buffers that were previously added
 * to the request via addBuffer() by setting \a flags to ReuseBuffers.
 */
void Request::reuse(ReuseFlag flags)
{
    LIBCAMERA_TRACEPOINT(request_reuse, this);

    _d()->reset();

    if (flags & ReuseBuffers) {
        for (const auto &[stream, buffer] : bufferMap_) {
            buffer->_d()->setRequest(this);
            _d()->pending_.insert(buffer);
        }
    } else {
        bufferMap_.clear();
    }

    status_ = RequestPending;

    controls_.clear();
    _d()->metadata_.clear();
}
