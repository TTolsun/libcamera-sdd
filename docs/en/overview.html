Discovery and pipeline selection

Start with CameraManager in src/libcamera/camera_manager.cpp. This object discovers devices and gives applications access to cameras. Only one instance may exist at a time. Creating a second instance before deleting the first results in undefined behavior.

Paragraph evidence · 1
  • src/libcamera/camera_manager.cppL283

After CameraManager::start() succeeds, the application can access cameras in the system. Success returns 0; failure returns a negative error code. This access condition no longer holds once the camera manager stops or the device is unplugged.

Paragraph evidence · 1
  • src/libcamera/camera_manager.cppL329

While the camera manager is running, use cameras() to obtain the list or get() to find a camera by ID. get() returns a null pointer if no camera is found. The caller must ensure that the camera manager is running.

Paragraph evidence · 1
  • src/libcamera/camera_manager.cppL368

PipelineHandler::match() in src/libcamera/pipeline_handler.cpp registers devices as cameras. It acquires the devices needed for one pipeline, creates camera objects, and registers them with the manager. If not all required devices are found, it must either acquire none or release those already acquired, then return false. See Pipeline Handler for implementation details.

Component responsibilities

Camera represents a camera that produces one or more image streams from a single image source. Applications use this object to configure and control the device and capture images.

Paragraph evidence · 1
  • src/libcamera/camera.cppL758

Camera objects are created with create(), and their lifetime is managed through std::shared_ptr. Their constructors and destructor are private, so do not construct or delete them directly. Compare their ownership rules with requests and buffers in Camera and request model.

Request creation and ownership

Camera::createRequest() may be called in the Configured or Running state. It returns an empty request for the application to associate with buffers and parameters. It returns a null pointer on error.

Paragraph evidence · 1
  • src/libcamera/camera.cppL1243

Ownership of the returned request passes to the caller. The caller may delete it in the completion handler or reset its state with Request::reuse() before reusing it. cookie is a caller-supplied value that can associate the request with an external resource at completion; libcamera does not interpret its meaning.

Capture-session states and resources

Prepare capture by acquiring, configuring, and then starting the camera. Once started, the camera can process requests until it is stopped. Release the camera when finished.

Request submission and completion

The camera must be in the Running state to submit a request through Camera::queueRequest(). The request must contain at least one capture buffer. A request without buffers is rejected without being queued.

Paragraph evidence · 1
  • src/libcamera/camera.cppL1308

A return value of 0 from queueRequest() means successful submission; capture completion is reported separately through requestCompleted. A negative return and missing completion after submission require different checks. Use Diagnose by failure stage to locate the code for the observed result.

Buffer completion and request completion

PipelineHandler::completeBuffer() signals buffer completion and updates the request’s internal buffer tracking. The request does not complete automatically when the last buffer finishes. The pipeline must call completeRequest() explicitly.

Paragraph evidence · 1
  • src/libcamera/pipeline_handler.cppL547

When investigating missing request completion, check buffer completion and request completion separately. See Pipeline Handler for the implementation contracts of both calls.

Thread boundaries and synchronization

Camera generally does not synchronize state-changing functions with each other. The caller must provide any necessary synchronization. When changing a state transition, also check the other state-changing functions called alongside it.

Paragraph evidence · 1
  • src/libcamera/camera.cppL780

PipelineHandler::completeRequest() must be called from the CameraManager thread. The pipeline must not access the request after this function returns. Do not extend this thread contract to all callbacks.

\brief Queue a request to the camera
 * \param[in] request The request to queue to the camera
 *
 * This function queues a \a request to the camera for capture.
 *
 * After allocating the request with createRequest(), the application shall
 * fill it with at least one capture buffer before queuing it. Requests that
 * contain no buffers are invalid and are rejected without being queued.
 *
 * Once the request has been queued, the camera will notify its completion
 * through the \ref requestCompleted signal.
 *
 * \context This function is \threadsafe. It may only be called when the camera
 * is in the Running state as defined in \ref camera_operation.
 *
 * \return 0 on success or a negative error code otherwise
 * \retval -ENODEV The camera has been disconnected from the system
 * \retval -EACCES The camera is not running so requests can't be queued
 * \retval -EXDEV The request does not belong to this camera
 * \retval -EINVAL The request is invalid
 * \retval -ENOMEM No buffer memory was available to handle the request
 */
