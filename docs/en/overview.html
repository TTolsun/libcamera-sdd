Terms in this document: IPA, Pipeline Handler
  • IPA (Image Processing Algorithms): A separate module (.so) that contains image quality algorithms. It reads the statistics sent by the ISP and calculates the ISP settings to use for the next frame. It is separated from the libcamera core so that manufacturers can provide it without publishing its source.
  • Pipeline Handler: A libcamera component that finds the media device of a specific hardware platform (IPU3, RKISP1, etc.), creates cameras, passes requests to the device, and returns their completion. There is one per platform.

Other terms can be found in Glossary.

Discovery and pipeline selection

CameraManager is the entry point of libcamera that enumerates devices and provides applications with access to the cameras in the system. According to the introductory comment, CameraManager owns all Camera objects and manages camera lifetimes by handling hot-plug and hot-unplug. CameraManager::Private::pipelineFactoryMatch repeatedly creates PipelineHandler from the given factory and provides as many matching pipelines as possible while each object's match(enumerator_.get()) returns true. When match returns false, the iteration stops, and a Debug log is recorded only when the match succeeds.

Only one CameraManager instance can exist at a time.

Execution check item: Creating a second CameraManager instance without deleting the existing instance results in undefined behaviour. Therefore, the calling side must delete the existing instance before creating a new instance.

If CameraManager::start() succeeds, the application can list and use the cameras in the system enumerated during startup, and this state continues until the camera manager is stopped or the camera is disconnected from the system. CameraManager::cameras() and CameraManager::get() must be called while the camera manager is running, and responsibility for ensuring this state rests with the caller.

Whoever implements match() must acquire all the required devices with MediaDevice::acquire() once all of them are found. Then the implementation must create a Camera instance, store it internally, register it with the camera manager, and return true. If not all the required devices are found, the implementation must either not acquire any device, or release the devices already acquired with MediaDevice::release() and then return false.

Responsibilities by component

The Camera class represents a camera that can create one or more image streams from a single image source. It provides the main interface for configuring and controlling the device and capturing image streams, and it is the central object that libcamera exposes externally.

libcamera manages the lifetime of Camera instances with std::shared_ptr<>. Instances must be created with the create() function, which returns a shared pointer. The constructors and destructor of Camera are declared private, so instances cannot be constructed or destroyed directly.

Request creation and ownership

The cookie of Camera::createRequest is an opaque input value for the application. This value is stored in the generated request and can be read again at any time with Request::cookie(). According to the source description, applications typically use this value in the request completion handler to associate the request with an external resource, and from libcamera's perspective, cookie is a completely opaque value. Camera::createRequest() can only be called when the camera is in the Configured or Running state, and on error, the function returns nullptr.

Ownership of the request returned by Camera::createRequest() passes to the caller, who is also responsible for deleting it. To requeue the same request instead of creating a new one, the caller must call Request::reuse() before queueing the request, to reset its status and associated controls. If flags & ReuseBuffers is true, Request::reuse(ReuseFlag) calls setRequest(this) on each buffer in bufferMap_ and adds it to _d()->pending_, so buffers already added with addBuffer() are retained and reused. If ReuseBuffers is not specified, bufferMap_ is cleared.

State and resources of the capture session

To prepare capture, the application must acquire the camera with acquire(), configure it with configure(), and then start it with start(). A started camera can process requests until it is stopped, and this period is the Running state. The full end path runs from Running via stop() through Stopping, returns to Configured after stopping, and then goes from Configured via release() to Available, releasing the camera. While the camera is not released, the application may repeat starting and stopping multiple times, and may also change the capture settings by reconfiguring the camera.

Request submission and completion

The application must attach at least one capture buffer to the request object returned by createRequest() before submitting it with Camera::queueRequest(). When a request submitted with Camera::queueRequest() finishes processing, the camera notifies completion through the requestCompleted signal. Camera::queueRequest() may be called only when the camera is in the Running state defined in camera_operation.

Buffer completion and request completion

The pipeline handler must call PipelineHandler::completeBuffer() to signal that one buffer of the request has completed. completeBuffer() notifies the application of the buffer completion and updates the request's internal buffer tracking state. If all buffers contained in the request have completed, the function returns true; otherwise, the function returns false. Even after the last buffer completes, the pipeline handler must explicitly call completeRequest().

Thread boundaries and synchronization

Functions that change the Camera state are generally not synchronized with each other by the Camera class, so if necessary, the caller must ensure synchronization between these functions. The caller of PipelineHandler::completeRequest() is the pipeline handler. The pipeline handler must call this function when notifying the camera of a completed request, and the call must be made from the CameraManager thread.

Scope of static evidence verification

Camera::start() checks the camera state through d->isAccessAllowed(Private::CameraConfigured) and stores its return value in ret. When ret is negative (ret < 0), start() returns that value unchanged through return ret;, and in this branch, neither the pipeline start call nor the state transition to Private::CameraRunning is executed. The -EACCES in the API comment means a state in which the camera cannot start, but from this code fragment alone it cannot be confirmed that isAccessAllowed() returns -EACCES, so the two values are not asserted to be the same. The item that the TODO comment asks to be documented is the camera start timing.

void CameraManager::Private::pipelineFactoryMatch(const PipelineHandlerFactoryBase *factory)
{
    CameraManager *const o = LIBCAMERA_O_PTR();

    /* Provide as many matching pipelines as possible. */
    while (1) {
        std::shared_ptr<PipelineHandler> pipe = factory->create(o);
        if (!pipe->match(enumerator_.get()))
            break;

        LOG(Camera, Debug)
            << "Pipeline handler \"" << factory->name()
            << "\" matched";
    }
}

\brief Reset the request for reuse
 * \param[in] flags Indicate whether or not to reuse the buffers
 *
 * Reset the status and controls associated with the request, to allow it to
 * be reused and requeued without destruction. This function shall be called
 * prior to queueing the request to the camera, in lieu of constructing a new
 * request. The application can reuse the buffers that were previously added
 * to the request via addBuffer() by setting \a flags to ReuseBuffers.
 */
void Request::reuse(ReuseFlag flags)
{
    LIBCAMERA_TRACEPOINT(request_reuse, this);

    _d()->reset();

    if (flags & ReuseBuffers) {
        for (const auto &[stream, buffer] : bufferMap_) {
            buffer->_d()->setRequest(this);
            _d()->pending_.insert(buffer);
        }
    } else {
        bufferMap_.clear();
    }

    status_ = RequestPending;

    controls_.clear();
    _d()->metadata_.clear();
}
