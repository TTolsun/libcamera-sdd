연동 순서와 구현 책임을 확인하고 설정·요청·정지 계약을 적용하세요.

이 문서의 용어: Pipeline Handler, IPA, 프록시
  • Pipeline Handler: 특정 하드웨어 플랫폼(IPU3, RKISP1 등)의 미디어 장치를 찾아 카메라를 만들고, 요청을 장치에 넣고 완료를 돌려주는 libcamera 구성 요소입니다. 플랫폼마다 하나씩 있습니다.
  • IPA (Image Processing Algorithms): 화질 알고리즘을 담은 별도 모듈(.so)입니다. ISP가 보낸 통계를 보고 다음 프레임에 쓸 ISP 설정값을 계산합니다. 제조사가 소스를 공개하지 않고 제공할 수 있도록 libcamera 본체와 분리되어 있습니다.
  • 프록시: IPA 모듈을 직접 부르지 않고, 같은 인터페이스로 호출을 받아 IPA 스레드나 별도 프로세스로 전달하는 대리 객체입니다. 빌드할 때 mojom 정의에서 자동 생성됩니다.

다른 용어는 용어집에서 찾을 수 있습니다.

연동 순서와 책임

애플리케이션은 촬영을 준비하기 위해 카메라를 확보하고 구성한 뒤 시작해야 하며, 시작된 카메라는 정지할 때까지 요청을 처리할 수 있고, 애플리케이션은 사용을 마치면 카메라를 해제해야 합니다. 애플리케이션은 카메라를 해제하지 않은 동안 여러 번 시작하고 정지할 수 있으며, 카메라를 재구성할 수도 있습니다. Camera 클래스는 카메라 상태에 영향을 주는 함수들을 일반적으로 서로 동기화하지 않으므로, 필요한 경우 호출자가 이 함수들의 동기화를 책임져야 합니다.

하드웨어와 공통 계층의 경계

PipelineHandler::match() 구현자는 단일 파이프라인에 필요한 모든 미디어 장치를 찾으면 MediaDevice::acquire()를 호출해 장치를 모두 확보한 뒤 해당 Camera 인스턴스를 하나 이상 생성하고 내부에 저장하며 카메라 매니저에 등록한 후 true를 반환해야 합니다. PipelineHandler::match() 구현자는 필요한 미디어 장치를 모두 찾지 못한 경우 아직 장치를 확보하지 않았다면 어떤 미디어 장치도 확보해서는 안 되며, 이미 일부를 확보했다면 확보한 장치를 모두 MediaDevice::release()로 해제하고 false를 반환해야 합니다. PipelineHandler::match()는 CameraManager 스레드에서 호출되며, true를 반환하면 새 PipelineHandler 인스턴스가 생성되고 그 인스턴스의 match()가 호출됩니다.

구현할 설정 인터페이스

generateConfiguration 호출자는 기본 구성을 가져오려는 사용 사례를 roles에 채워야 합니다. generateConfiguration()이 반환하는 구성에는 선택된 스트림과 각 스트림의 기본 파라미터 정보가 포함됩니다. PipelineHandler::generateConfiguration()은 요청된 roles를 충족할 수 있으면 유효한 CameraConfiguration을 반환해야 하고, 그렇지 않으면 null 포인터를 반환해야 합니다. PipelineHandler::generateConfiguration()은 어떤 스레드에서든 호출될 수 있으므로, 구현은 스레드 안전성을 갖춰야 합니다.

PipelineHandler::generateConfiguration() 구현자는 파이프라인 핸들러 내의 camera 상태를 변경해서는 안 됩니다. PipelineHandler::configure()에 전달되는 설정은 CameraConfiguration::validate()로 검증된 상태가 보장되므로, 파이프라인 핸들러 구현은 추가 검증을 해서는 안 됩니다. PipelineHandler::configure()의 구현은 자체 CameraConfiguration 파생 클래스에 저장된 모든 사용자 정의 필드에 의존할 수 있습니다. PipelineHandler::configure() 구현자는 카메라를 구성할 때 StreamConfiguration::setStream()을 사용하여 CameraConfiguration의 각 StreamConfiguration 항목에 Stream 인스턴스를 연결해야 합니다.

PipelineHandler::configure()는 CameraManager 스레드에서 호출되며, 구현은 성공하면 0을 반환하고 실패하면 음수 오류 코드를 반환해야 합니다.

요청을 장치에 전달하고 반환하기

queueRequestDevice 구현자는 스트림에 연결된 버퍼 집합과 파라미터 집합을 담은 요청을 처리할 때, 요청에 제공된 버퍼에 캡처된 프레임에 해당 파라미터가 적용되도록 장치를 설정해야 합니다. queueRequestDevice 구현자는 성공하면 0을, 실패하면 음수 오류 코드를 반환해야 합니다. PipelineHandler::queueRequestDevice()는 CameraManager 스레드에서 호출됩니다.

파이프라인 핸들러는 요청의 버퍼 완료를 알리기 위해 CameraManager 스레드에서 completeBuffer()를 호출해야 합니다. 이 함수는 애플리케이션에 버퍼 완료를 통지하고 요청 내부의 버퍼 추적 정보를 갱신합니다. 마지막 버퍼가 완료되어도 요청은 자동으로 완료되지 않으므로 파이프라인 핸들러는 completeRequest()를 명시적으로 호출해 요청을 완료해야 합니다.

IPA 모듈 선택과 실패 조건

createIPA는 module을 호출할 때 이름을 나타내는 name, 최소 버전을 나타내는 minVersion, 최대 버전을 나타내는 maxVersion을 순서대로 전달합니다. IPAManager::module은 모듈을 순회하며 이름과 허용 버전 범위에 대해 첫 match가 있으면 해당 모듈을 반환하고 검색을 끝냅니다. 끝까지 일치하는 모듈이 없으면 nullptr을 반환합니다. createIPA는 module의 결과를 m에 받고, !m이면 nullptr을 반환합니다.

createIPA 내부 람다는 isSignatureValid(m)이 참이면 T::Threaded 객체를 생성하고, 거짓이면 T::Isolated 객체를 생성합니다. createIPA는 생성한 프록시의 isValid 검사에 실패하면 오류 메시지 Failed to load proxy를 기록하고 nullptr을 반환합니다. createIPA는 생성한 프록시가 유효성 검사를 통과하면 해당 프록시를 반환합니다.

정지와 오류 처리의 책임

PipelineHandler::stop()은 먼저 waitingRequests.swap(data->waitingRequests_)를 호출한 다음 stopDevice(camera)를 호출합니다. PipelineHandler::stop()은 stopDevice() 내부에서 completeRequest()가 호출될 때 대기 요청이 다시 큐에 들어가지 않도록 모든 대기 요청을 따로 옮깁니다. stopDevice() 구현자는 실행 중인 모든 스트림의 캡처와 요청 처리를 즉시 중단하고, 해당 장치의 미완료 요청을 모두 취소해 즉시 오류 상태로 완료해야 합니다.

PipelineHandler::stop()은 stopDevice()를 호출한 뒤 대기 요청을 차례로 취소하고 doQueueRequest()에 전달하며, 이 경로에서 요청에 순번을 부여하고 completeRequest()에서 완료할 수 있도록 queuedRequests_에 일시적으로 추가합니다. PipelineHandler::stop()은 대기 요청을 처리한 뒤 두 ASSERT로 queuedRequests_와 waitingRequests_가 비어 있는지 확인하고 requestSequence_에 0을 저장합니다.

구현 뒤 확인할 계약과 실행 한계

파이프라인 핸들러는 completeRequest가 반환된 뒤에는 더 이상 관리하지 않는 해당 요청에 접근해서는 안 됩니다. 파이프라인 핸들러는 완료된 요청을 순서 제약 없이 completeRequest에 전달할 수 있으며, 이 함수는 요청을 제출 순서대로 애플리케이션에 반환합니다. 파이프라인 핸들러는 completeRequest를 CameraManager 스레드에서 호출해야 합니다.

 *
 * Releasing the camera device allows other users to acquire exclusive access
 * with the acquire() function.
 *
 * \context This function may only be called when the camera is in the
 * Available or Configured state as defined in \ref camera_operation, and shall
 * be synchronized by the caller with other functions that affect the camera
 * state.
 *
 * \return 0 on success or a negative error code otherwise
 * \retval -EBUSY The camera is running and can't be released
 */
int Camera::release()
{
    Private *const d = _d();

    int ret = d->isAccessAllowed(Private::CameraAvailable,
                     Private::CameraConfigured, true);
    if (ret < 0)
        return ret == -EACCES ? -EBUSY : ret;

                       ConnectionTypeBlocking, this);

}

void PipelineHandler::stop(Camera *camera)
{
    /*
     * Take all waiting requests so that they are not requeued in response
     * to completeRequest() being called inside stopDevice(). Cancel them
     * after the device to keep them in order.
     */
    Camera::Private *data = camera->_d();
    std::queue<Request *> waitingRequests;
    waitingRequests.swap(data->waitingRequests_);

    /* Stop the pipeline handler and let the queued requests complete. */
    stopDevice(camera);

    /* Cancel and signal as complete all waiting requests. */
    while (!waitingRequests.empty()) {
        Request *request = waitingRequests.front();
        waitingRequests.pop();

        /*
         * Cancel all requests by marking them as cancelled and calling
         * doQueueRequest() instead of cancelRequest(). This ensures
         * that the requests get a sequence number and are temporarily
         * added to queuedRequests_ so they can be properly completed in
         * completeRequest().
         */
        request->_d()->cancel();
        doQueueRequest(request);
    }

    /* Make sure no requests are pending. */
    ASSERT(data->queuedRequests_.empty());
    ASSERT(data->waitingRequests_.empty());

    data->requestSequence_ = 0;
}
