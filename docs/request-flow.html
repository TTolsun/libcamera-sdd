요청 생성과 소유권

Camera::createRequest(cookie)의 cookie는 애플리케이션이 사용하는 불투명한 입력입니다. 이 값은 요청에 저장되며 Request::cookie()로 언제든 읽을 수 있고, libcamera 관점에서는 완전히 불투명합니다. 애플리케이션은 보통 요청 완료 핸들러에서 요청을 외부 리소스에 연결하는 데 이 값을 사용합니다. Camera::createRequest()는 카메라가 Configured 또는 Running 상태일 때만 호출할 수 있으며, 오류가 발생하면 nullptr을 반환합니다.

Camera::createRequest()가 반환한 요청의 소유권은 호출자에게 넘어가며, 호출자는 요청을 삭제할 책임이 있습니다. 호출자는 새 요청을 만들지 않고 같은 요청을 다시 큐에 넣으려면 큐에 넣기 전에 Request::reuse()를 호출해 요청 상태와 연결된 컨트롤을 초기화해야 합니다. Request::reuse()는 ReuseBuffers를 지정하면 addBuffer()로 추가한 기존 버퍼를 요청에 다시 연결해 재사용하고 지정하지 않으면 bufferMap_을 비우며, 버퍼에 연결된 펜스는 재사용하지 않으므로 펜스를 사용할 때는 ReuseBuffers를 쓰지 않도록 권고합니다.

소유권과 두 완료 경계

Camera::createRequest() 호출자는 반환된 Request의 소유권을 받으며 삭제할 책임이 있습니다. 호출자는 완료 핸들러에서 요청을 삭제하거나 Request::reuse()로 상태를 초기화한 뒤 재사용할 수 있습니다. Request::addBuffer()는 버퍼 참조를 요청에 저장하며, 호출자는 요청 완료 콜백이 호출될 때까지 버퍼가 유효하도록 해야 합니다. 파이프라인 핸들러는 completeRequest() 또는 cancelRequest()가 반환된 뒤 해당 요청에 접근해서는 안 됩니다.

정지와 연결 해제를 구분하기

UVC의 정상 버퍼 반환과 STREAMOFF 성공 시 남은 버퍼 취소는 imageBufferReady에서 completeBuffer와 completeRequest를 거쳐 같은 requestCompleted 알림으로 이어질 수 있습니다. Developer는 이 슬롯에서 RequestComplete와 RequestCancelled를 구별하고 버퍼별 FrameSuccess로 영상 사용 여부를 판단해야 하며, RequestComplete에도 FrameError가 있을 수 있고 취소된 버퍼는 FrameCancelled입니다. Vendor의 장치 검증 계획은 첫 실행에서 정상 촬영하고 둘째 실행에서 미완료 요청을 남긴 채 stop()을 호출하며, 수신 루프를 처리해 제출별 알림 횟수와 미수신 여부, 요청과 버퍼 상태를 기록하는 것입니다. 다른 스레드에 큐잉된 슬롯은 stop() 반환 뒤에도 실행될 수 있습니다.
