요청 준비와 장치 큐

PipelineHandler::registerRequest()는 요청이 생성될 때 호출됩니다. 이 시점에 pipeline handler가 해당 요청에 필요한 일회성 초기화를 수행할 수 있습니다. PipelineHandler::registerRequest()에서 request->_d()->prepared 신호에 연결된 람다 콜백이 실제로 호출하는 함수는 doQueueRequests입니다. PipelineHandler::queueRequest는 요청이 가리키는 카메라의 내부 waitingRequests_ 큐에 요청을 추가한 뒤, 같은 요청의 prepare 호출에 300ms 시간 인자를 전달합니다.

Request::Private::prepare는 pending_에 있는 각 FrameBuffer의 획득 펜스마다 fd를 읽기 대기하는 EventNotifier를 만들어 연결하며, 펜스가 신호되면 notifierActivated가 호출됩니다. 대기할 펜스가 없으면 notifiers_가 비어 있게 되므로 Request::prepared 신호를 즉시 발생시키고 바로 반환합니다. 선택적 timeout 인자가 0ms가 아니고 대기할 펜스가 있을 때에만 Timer를 만들어 timeout 시간으로 시작하며, 만료 시점에 모든 펜스가 올바르게 신호되지 않았다면 Request가 취소되고 Request::prepared 신호가 발생합니다. 이 타이머는 Request 생성자가 아니라 prepare 호출 시점에 만들어지는데, 파이프라인 핸들러 스레드에 바인딩되도록 하기 위해서입니다.

PipelineHandler::doQueueRequests()에서 data->queuedRequests_의 크기가 maxQueuedRequestsDevice_와 같으면 break가 실행되어 while 반복이 중단되므로, 이 호출에서는 대기 중인 요청을 더 꺼내 doQueueRequest()로 넘기지 않습니다. doQueueRequests()는 waitingRequests_ 선두 요청의 request->_d()->prepared_가 false이면 break를 실행하여 while 반복을 중단합니다. 이 검사는 pop()보다 먼저 수행되므로 준비되지 않은 요청은 대기열 맨 앞에 그대로 남습니다. 따라서 이번 호출에서는 그 뒤에 있는 요청도 doQueueRequest()로 넘기지 않고 종료합니다.

doQueueRequest는 요청을 data->queuedRequests_에 추가한 뒤, request->_d()->sequence_에 data->requestSequence_의 증가 전 값을 대입하고 그다음 data->requestSequence_를 증가시킵니다. doQueueRequest에서 request->_d()->cancelled_가 참이면 completeRequest(request)를 호출한 뒤 return으로 doQueueRequest 함수를 즉시 종료합니다. 따라서 이 분기는 queueRequestDevice 호출과 cancelRequest 처리보다 먼저 반환합니다.

doQueueRequest는 request->_d()->cancelled_가 설정된 요청을 취소 분기에서 조기 반환시킨 뒤, 취소되지 않은 요청에 한해 queueRequestDevice(camera, request)를 호출하고 그 결과를 ret에 저장합니다. doQueueRequest에서 queueRequestDevice(camera, request)의 반환값 ret가 0이 아닐 때, 즉 if (ret) 조건이 참이면 cancelRequest(request)를 호출합니다. queueRequestDevice의 구현자는 요청에 포함된 매개변수가 요청에 제공된 버퍼에 캡처되는 프레임에 적용되도록 장치를 프로그래밍해야 합니다(shall). 요청은 스트림과 연결된 버퍼 집합과 매개변수 집합을 포함합니다.

버퍼 완료와 요청 반환

PipelineHandler::completeBuffer는 먼저 request가 속한 카메라의 bufferCompleted 시그널을 emit하여 애플리케이션에 버퍼 완료를 알립니다. 이어서 request->_d()->completeBuffer(buffer)를 호출하여 요청의 내부 버퍼 추적을 갱신합니다. 다만 이 함수는 마지막 버퍼가 완료되어도 요청을 자동으로 완료하지 않습니다.

버퍼 완료에서 요청 반환까지

마지막 버퍼의 완료가 요청을 자동 완료하지 않습니다. 핸들러의 명시적 요청 완료 통지가 필요합니다.

completeBuffer는 요청의 마지막 버퍼가 완료되어도 요청을 자동으로 완료하지 않습니다. 원문에 따르면 이는 파이프라인 핸들러가 여전히 필요한 작업을 수행할 기회를 갖도록 하기 위한 것입니다. 파이프라인 핸들러는 요청을 완료하기 위해 completeRequest()를 명시적으로 호출해야 합니다. completeRequest가 반환한 뒤 해당 요청은 파이프라인 핸들러가 더 이상 관리하지 않으며, 파이프라인 핸들러는 이 함수가 반환된 뒤 요청에 접근하지 않아야 합니다.

completeRequest는 요청을 제출 순서대로 애플리케이션에 반환하도록 보장하는 함수입니다. 파이프라인 핸들러는 완료된 요청이면 어떤 요청에 대해서도 completeRequest를 호출할 수 있으며, 이때 호출 순서에 대한 제약은 없습니다.

completeRequest의 while 루프는 queuedRequests_의 맨 앞 요청 상태가 Request::RequestPending이면 break를 실행하여 루프를 중단합니다. 이 경우 해당 요청은 pop_front()로 제거되지 않고, camera->requestComplete()도 호출되지 않은 채 큐의 맨 앞에 남습니다. 따라서 그 뒤에 있는 요청들은 이 루프에서 검사되지 않습니다.

completeRequest가 대기 요청 전달을 재개하기 위해 마지막에 호출하는 함수는 doQueueRequests(camera)입니다. 소스 주석에는 이 호출이 대기 중인 요청을 파이프라인에 큐잉할 수 있도록 허용한다고 적혀 있습니다. 이 호출은 completeRequest 안의 while 루프가 끝난 뒤에 실행됩니다.

completeBuffer와 completeRequest는 모두 CameraManager 스레드에서 호출되어야 합니다. 파이프라인 핸들러는 요청의 버퍼 부분이 완료되면 completeBuffer를 호출해야 하고, 요청이 완료되면 completeRequest를 호출해야 합니다. cancelRequest는 먼저 request->_d()->cancel()을 호출하여 요청을 취소합니다. 그다음 completeRequest(request)를 호출하여 요청의 완료를 알립니다.

장치 요청 한도와 대기 큐

PipelineHandler 생성자 선언에서 maxQueuedRequestsDevice의 기본값은 32입니다. maxQueuedRequestsDevice_가 제한하는 요청 수는 underlying hardware에 queue되는 요청, 즉 장치 쪽 큐에 해당합니다. 나머지 요청은 internal waiting queue에서 대기하며 나중에 queue됩니다.

애플리케이션이 장치 한도보다 많은 요청을 제출하면, 한도를 넘는 나머지 요청은 파이프라인 핸들러 내부의 internal waiting queue에서 기다립니다. 장치로는 한 시점에 maxQueuedRequestsDevice_ 개수의 요청만 큐잉되며, 나머지 요청은 나중 단계에서 큐잉됩니다. 애플리케이션은 원하는 만큼 요청을 제출할 수 있습니다(may).

void PipelineHandler::doQueueRequest(Request *request)
{
    LIBCAMERA_TRACEPOINT(request_device_queue, request);

    Camera *camera = request->_d()->camera();
    Camera::Private *data = camera->_d();
    data->queuedRequests_.push_back(request);

    request->_d()->sequence_ = data->requestSequence_++;

    if (request->_d()->cancelled_) {
        completeRequest(request);
        return;
    }

    int ret = queueRequestDevice(camera, request);
    if (ret)

}

/**
 * \brief Queue prepared requests to the device
 *
 * Iterate the list of waiting requests and queue them to the device one
 * by one if they have been prepared.
 */
void PipelineHandler::doQueueRequests(Camera *camera)
{
    Camera::Private *data = camera->_d();

\brief Prepare the Request to be queued to the device
 * \param[in] timeout Optional expiration timeout
 *
 * Prepare a Request to be queued to the hardware device by ensuring it is
 * ready for the incoming memory transfers.
 *
 * This currently means waiting on each frame buffer acquire fence to be
 * signalled. An optional expiration timeout can be specified. If not all the
 * fences have been signalled correctly before the timeout expires the Request
 * is cancelled.
 *
 * The function immediately emits the prepared signal if all the prepare
 * operations have been completed synchronously. If instead the prepare
 * operations require to wait the completion of asynchronous events, such as
 * fences notifications or timer expiration, the prepared signal is emitted upon
 * the asynchronous event completion.
 *
 * As we currently only handle fences, the function emits the prepared signal
 * immediately if there are no fences to wait on. Otherwise the prepared signal
 * is emitted when all fences have been signalled or the optional timeout has
 * expired.
 *
 * If not all the fences have been correctly signalled or the optional timeout
 * has expired the Request will be cancelled and the Request::prepared signal
 * emitted.
 *
 * The intended user of this function is the PipelineHandler base class, which
 * 'prepares' a Request before queuing it to the hardware device.
 */
void Request::Private::prepare(std::chrono::milliseconds timeout)
{
    /* Create and connect one notifier for each synchronization fence. */
    for (FrameBuffer *buffer : pending_) {
        const Fence *fence = buffer->_d()->fence();
        if (!fence)
            continue;

        auto [it, inserted] = notifiers_.try_emplace(buffer, fence->fd().get(), EventNotifier::Type::Read);
        ASSERT(inserted);

        it->second.activated.connect(this, [this, buffer] {
            notifierActivated(buffer);
        });
    }

    if (notifiers_.empty()) {
        emitPrepareCompleted();
        return;
    }

    /*
     * In case a timeout is specified, create a timer and set it up.
     *
     * The timer must be created here instead of in the Request constructor,
     * in order to be bound to the pipeline handler thread.
     */
    if (timeout != 0ms) {
        timer_ = std::make_unique<Timer>();
        timer_->timeout.connect(this, &Request::Private::timeout);
        timer_->start(timeout);
    }
}

/**
 * \brief Signal request completion
 * \param[in] request The request that has completed
 *
 * The pipeline handler shall call this function to notify the \a camera that
 * the request has completed. The request is no longer managed by the pipeline
 * handler and shall not be accessed once this function returns.
 *
 * This function ensures that requests will be returned to the application in
 * submission order, the pipeline handler may call it on any complete request
 * without any ordering constraint.
 *
 * \context This function shall be called from the CameraManager thread.
 */
void PipelineHandler::completeRequest(Request *request)
{
    Camera *camera = request->_d()->camera();

    request->_d()->complete();

    Camera::Private *data = camera->_d();

    while (!data->queuedRequests_.empty()) {
        Request *req = data->queuedRequests_.front();
        if (req->status() == Request::RequestPending)
            break;

        ASSERT(!req->hasPendingBuffers());
        data->queuedRequests_.pop_front();
        camera->requestComplete(req);
    }

    /* Allow any waiting requests to be queued to the pipeline. */
    doQueueRequests(camera);
}
